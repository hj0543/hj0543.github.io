프로젝트 개요

마음에 드는 집을 찾은 뒤, 내 생활과 형편에도 맞는지 판단할 수 있을까?

Homefit은 매물과 주변 환경, 예상 대출 부담을 함께 비교하도록 만든 주거 탐색 서비스입니다. 직접 집을 알아보면서 매물은 부동산 앱에서, 학교와 역은 지도에서, 대출 조건은 금융기관 사이트에서 확인하고 정보를 다시 모아야 했던 경험에서 출발했습니다.

SSAFY 1학기 종합 프로젝트로 2명이 함께 진행했습니다. 저는 지도 검색과 관심 매물 비교, 대출 시뮬레이션 UI/UX, 공공데이터 연동 등을 맡아 담당 기능의 프론트엔드와 백엔드를 함께 구현했습니다.

문제 정의와 목표

집을 찾을 때 필요한 정보는 가격 하나로 끝나지 않았습니다. 마음에 드는 매물을 찾은 뒤에도 생활 환경과 대출 조건을 따로 확인해야 했고, 후보를 바꿀 때마다 같은 비교를 반복해야 했습니다. 저는 이 정보를 Notion에 모아 직접 비교표를 만들었습니다.

이 경험을 바탕으로 **‘내 조건에 맞는 매물 찾기 → 같은 기준으로 비교하기 → 예상 자금 부담 확인하기’**를 서비스의 핵심 흐름으로 정했습니다.

  • 탐색: 가격·면적과 주거 선호에 맞는 후보를 찾을 수 있는가?
  • 비교: 학교·교통·생활 인프라와 실거래가를 같은 기준으로 볼 수 있는가?
  • 자금 확인: 프로젝트에서 반영한 대출 조건과 예상 상환 부담을 이해할 수 있는가?

목표는 사용자가 여러 곳의 정보를 다시 정리해야 하는 과정을 서비스 안에서 연결하는 것이었습니다.

핵심 기획 결정

1. 매물 검색 다음에 비교와 대출 확인이 이어지도록 설계

지도에서 후보를 찾고 관심 매물로 저장한 뒤, 가격·면적·학군·역세권·실거래가 추이를 한 표에서 비교하도록 구성했습니다. 대출 시뮬레이션에서도 관심 매물을 선택해 해당 주택과 사용자의 금융 조건을 함께 확인하도록 연결했습니다.

매물 선택 방식은 드래그 앤 드롭에서 관심 매물 목록 중 선택하는 방식으로 바꿨습니다. 사용자가 저장한 후보를 다음 단계에서 명시적으로 고를 수 있게 하고, 선택한 매물에 대한 자격 판정과 예상 금리·상환 그래프로 이어지도록 했습니다.

2. 비교에 필요한 데이터를 확보할 수 있는 지역으로 범위 조정

처음에는 동탄을 대상 지역으로 정했지만, 신축 단지의 세대 수·주차 대수·용적률 등 비교에 필요한 정보가 부족했습니다. 지도에 매물을 표시하더라도 의도한 비교 경험을 만들기 어려운 상태였습니다.

이에 따라 데이터가 충분한 분당으로 대상을 바꾸고 안양·광명을 추가했습니다. 대상 지역을 정하는 기준을 비교에 필요한 데이터를 확보할 수 있는지로 조정한 것입니다.

외부 API의 지연과 서로 다른 응답 형식도 고려했습니다. 화면에서 매번 원본 API를 호출하는 대신, 필요한 정보를 미리 수집·전처리해 저장하고 지도에서는 현재 영역의 데이터를 조회하도록 구현했습니다. 제공하려는 정보와 데이터의 확보·갱신 방식을 함께 정해야 한다는 것을 배웠습니다.

3. 비교 점수와 대출 판정에 기준과 이유를 부여

학교가 가까운 것과 해당 학교의 통학구역에 속하는 것은 다른 정보였습니다. 저는 학교와의 거리뿐 아니라 학구도 데이터를 활용해 통학구역을 판정하고, 학군·역세권 점수를 매물 찾기·비교·AI 추천에서 공통으로 사용하도록 정리했습니다.

같은 매물의 점수가 화면마다 다르면 비교 기준이 흔들립니다. 따라서 계산을 공통 서비스로 모으고, AI 매물 분석에도 화면에서 사용하는 학군·학교 거리 정보를 전달했습니다.

대출 시뮬레이션은 프로젝트 당시의 정책대출 공시 기준을 규칙표로 정리한 뒤 구현했습니다. 결과에는 자격 충족 여부와 함께 충족한 핵심 조건과 불가 사유를 표시했습니다. 사용자가 결과를 이해하고 다음에 무엇을 확인해야 할지 판단할 수 있게 하기 위한 결정이었습니다.

검색·비교·추천에 쓰이는 계산 기준을 공유하고, 대출 판정 기준은 문서와 구현을 함께 관리하도록 구성했습니다. AI 리포트는 매물과 주변 데이터를 설명하는 보조 정보로 연결했습니다.

추천과 분석 결과를 기다리는 과정도 이용 흐름의 일부로 봤습니다. 동일 입력의 리포트는 저장해 재사용하되, 대화 맥락이 달라지는 챗봇 요청은 캐시 대상에서 제외했습니다.

담당 역할과 협업

2인 팀에서 기능 단위로 역할을 나누고, 각자 담당 기능의 화면부터 API·데이터 연동까지 구현했습니다. 제 담당 영역은 다음과 같습니다.

  • 탐색·비교: 지도 기반 매물 검색과 인프라 표시, 관심 매물 비교표·요약·실거래가 그래프
  • 대출 이용 흐름: 관심 매물 선택부터 자격 판정, 우대금리 계산과 상환 그래프까지의 UI/UX 설계·구현
  • 데이터와 판단 기준: 공공데이터 수집·전처리·적재, 학군·역세권 계산과 추천 가중치 구현
  • 접근과 응답: 소셜 로그인, AI 매물 리포트 캐싱과 챗봇 프롬프트 개선

구현 전에 담당 기능과 API 이름을 맞추고, 상대가 작업 중인 파일을 수정해야 할 때는 먼저 공유했습니다. 기획서·API 명세·ERD·정책대출 규칙표를 기준 문서로 관리하고, 실제 모델에 맞춰 갱신했습니다.

기능을 처음부터 끝까지 맡으면서 화면의 요구사항이 어떤 데이터와 처리 과정으로 이어지는지 확인할 수 있었습니다. 다만 서로의 담당 코드를 충분히 검토하지 못한 점은 과제로 남았습니다.

결과와 검증 범위

  • 구현 결과: 지도 검색·관심 매물 비교·대출 시뮬레이션으로 이어지는 흐름과 AI 분석·상담 기능 구현
  • 데이터 범위: 분당·안양·광명을 대상으로 공공데이터를 수집하고, 실거래 데이터를 바탕으로 만든 가상 매물을 활용
  • 검증 범위: 추천 점수와 매물 API 일부 테스트 수행. 외부 사용자를 위한 배포와 화면 테스트는 후속 과제로 남음

당시 결과물은 가상 매물을 활용한 프로젝트였습니다. 실제 매물의 수집·갱신과 배포를 갖춘 뒤, 사용자가 같은 후보를 반복해서 검색하지 않고 비교와 자금 확인까지 진행할 수 있는지 검증할 필요가 있습니다.

다음 단계에서는 핵심 화면과 API를 점검하고, 대출 판정 이유와 예상 상환 부담을 사용자가 어떻게 이해하는지 확인하고 싶습니다. 후보를 바꾸면서도 비교 기준을 유지할 수 있는지, 데이터가 부족한 항목에서 어떤 안내가 필요한지도 함께 살펴보려고 합니다.

세부 기능

  • 지도 기반 매물 검색: Kakao Map 위에서 가격·면적·층·방 개수·역세권·학군 조건으로 아파트/오피스텔 매물을 필터링하고, 축척에 따라 개별 마커와 행정구역 집계 오버레이를 전환합니다.
  • 인프라 핀: 지하철역, 초등학교, 병원, 약국, 마트 등 생활 인프라를 지도 위에 함께 표시합니다.
  • 관심 매물 비교: 북마크한 매물을 골라 가격, 면적, 학군, 역세권, 실거래가 추이 그래프를 한 표에서 비교하고 종합 추천 문구를 제공합니다.
  • 대출 시뮬레이션: 연소득·자산·기존 대출을 반영해 DSR/LTV를 계산하고, 디딤돌대출·보금자리론의 자격 충족 여부와 우대금리 적용 예상 금리, 월 상환 그래프를 보여줍니다.
  • AI 매물 추천 및 상담: 금융·선호 조건을 점수화해 매물을 추천하고, OpenAI 기반 매물 분석 리포트와 부동산/대출 상담 챗봇을 제공합니다.
  • 부동산 알아가기: 부동산 용어 사전, 실시간 인기 검색어, 네이버 뉴스 큐레이션, 지역 커뮤니티를 제공합니다.
  • 회원 관리: 이메일 회원가입/로그인, Google·Kakao 소셜 로그인, 공인중개사 계정 분리, 마이페이지 금융·선호 정보 관리

담당 구현 범위

SSAFY 1학기 종합 프로젝트(관통 프로젝트)로 진행했으며, 페어와 기능 단위로 나누어 각자 프론트엔드와 백엔드를 모두 구현했습니다.

  • 로그인·회원가입·소셜 로그인: JWT 기반 인증, Google/Kakao OAuth 연동, 공인중개사 계정 분리 및 인증 수단 추가
  • 지도 기반 매물 검색: bbox 기반 매물 조회 API, 축척별 마커/행정구역 집계 전환, 인프라·학교 핀, 지역 검색
  • 관심 매물 비교: 비교 판단 로직을 백엔드 서비스로 모아 비교표와 종합 요약을 생성, 실거래가 추이 그래프
  • 대출 시뮬레이션 UI/UX: 관심 매물 선택 → 정책대출 자격 판정 → 우대금리 계산 → 상환 그래프 흐름 설계, 게이지/차트 컴포넌트 구현
  • 공공데이터 API 연동: 국토교통부 실거래가, 금융감독원 FINLIFE, 한국주택금융공사 HF, NEIS, Kakao Local, ODsay 데이터 수집·전처리·적재 파이프라인 구축
  • 추천 점수 로직: 학군 점수(학구도 point-in-polygon 판정 + 학원 밀집도), 역세권 점수(도보시간·대중교통 시간), 북마크 피드백 가중치
  • AI 기능: 매물 분석 리포트 캐싱, 챗봇 프롬프트 개선, 응답 시간 단축

시스템 아키텍처

  • Frontend: Vue 3 + Vite, Pinia, Kakao Map JavaScript SDK
  • Backend: Django REST Framework (인증, 매물, 대출, 커뮤니티, 추천), SimpleJWT
  • AI Server: FastAPI — OpenAI 응답 SSE 스트리밍, 네이버 뉴스 검색 라우터
  • External APIs: 국토교통부 실거래가, FINLIFE, HF, NEIS 학교알리미, SGIS, Kakao Local, ODsay, Naver News, Google/Kakao OAuth
  • Data Pipeline: 외부 API → 수집 스크립트 → CSV 전처리 → Django management command로 DB 적재

ERD

  • accounts: User(이메일 로그인 식별자, 금융·선호 정보 JSON), SocialAccount(provider + provider_id 복합 유니크)
  • properties: House, Deal(실거래), FakeListing(매물), SubwayStation, School, SchoolZone(학구도 폴리곤), LocalPlace(생활 인프라), ComplexStationWalk/ComplexSchoolWalk(도보시간), ListingBookmark
  • loans: LoanProduct, LoanProductOption, PolicyLoanRate, JeonseLoanRate
  • ai: AIConversation, AIMessage, AIReportCache
  • community / articles / domain / notifications: 지역 커뮤니티, 게시글, 용어 사전, 알림

기술적 고민 및 문제 해결

공공데이터 API의 응답 지연과 데이터 결손

문제 — 국토교통부 실거래가 API는 XML 응답에 페이지당 건수 제한이 있고 호출마다 수 초가 걸려, 지도를 움직일 때마다 실시간으로 호출하면 화면이 멈추는 수준이었습니다. 응답에 시도·시군구명과 좌표가 없어 그대로는 지도에 올릴 수도 없었고, Kakao Local·ODsay도 매물마다 실시간 호출하면 쿼터와 지연 문제가 동일하게 발생했습니다.

해결 — 화면에서 외부 API를 직접 호출하지 않는 구조로 바꿨습니다. 수집 스크립트가 API를 배치로 호출해 CSV로 저장하고, 전처리 단계에서 시군구 코드 역매핑과 Kakao 주소 지오코딩으로 좌표를 채운 뒤 management command로 DB에 적재했습니다. 지하철역 도보시간, 생활 인프라 핀도 같은 방식으로 미리 적재하고, 서비스에서는 현재 지도 bbox 범위의 DB 조회만 수행하도록 했습니다.

효과 — 지도 이동 시 응답이 외부 API 지연에 영향을 받지 않게 되었고, 같은 CSV를 반복 적재해도 update_or_create로 중복이 생기지 않아 데이터 갱신도 안정적으로 할 수 있게 되었습니다.

학구도 폴리곤 기반 학군 판정

문제 — 매물이 어느 초등학교 통학구역·중학교 학군에 속하는지 판정하려면 GeoJSON 폴리곤에 대한 point-in-polygon 검사가 필요한데, 목록 조회 때마다 전체 학구도를 순회하면 매물 수 × 폴리곤 수만큼 연산이 늘어났습니다.

해결 — 학구도마다 bbox를 저장해 두고, 매물 좌표가 bbox 안에 드는 후보만 먼저 걸러낸 뒤 그 후보에만 point-in-polygon(구멍이 있는 MultiPolygon 포함)을 적용했습니다. 폴리곤 GeoJSON은 목록 응답에 포함하지 않고 지도에서 학군 오버레이를 켤 때만 별도 API로 내려받도록 분리했습니다. 학군 점수는 교과목 학원만 반영하도록 기준을 조정해 매물 찾기와 AI 추천이 같은 계산 로직을 공유하게 했습니다.

효과 — 매물 목록과 단지 상세에 학군 요약과 education_score를 포함해도 응답 속도가 유지되었고, AI 매물 분석에도 실제 학군·학교 거리 컨텍스트를 함께 전달할 수 있었습니다.

정책대출 자격 판정과 우대금리 계산

문제 — 디딤돌대출·보금자리론은 무주택 여부, 부부합산 소득, 순자산, 주택가격, 전용면적 조건이 신혼·다자녀 여부에 따라 달라지고, 우대금리는 중복 불가 항목과 중복 가능 항목이 섞여 있어 단순 조건문으로는 유지보수가 어려웠습니다.

해결 — HF·주택도시기금 공시 기준을 규칙표 문서로 먼저 정리하고, 프론트 유틸이 그 표를 기준으로 동작하도록 구현했습니다. 기준 금리는 HF 정책대출 금리 API에서 받은 값을 쓰고 우대금리를 차감해 예상 적용 금리를 계산하며, 화면에는 신청 가능/불가만이 아니라 충족한 핵심 조건과 불가 사유를 함께 보여주도록 했습니다. 매물 선택 방식은 드래그 앤 드롭에서 관심 매물 목록 중 선택하는 방식으로 바꿔 진입 장벽을 낮췄습니다.

효과 — 사용자가 자기 상황에서 어떤 정책 상품을 신청할 수 있고 무엇이 부족한지 바로 확인할 수 있게 되었고, 규칙 변경 시 문서와 유틸만 수정하면 되도록 구조를 분리했습니다.

AI 매물 분석 리포트의 비용과 지연

문제 — 단지 상세에서 AI 분석 리포트를 요청하면 매번 OpenAI를 호출해 수 초의 지연과 비용이 발생했고, 같은 단지를 여러 사용자가 조회해도 동일한 응답을 반복 생성했습니다. 추천 API는 매물별 추천 사유 생성까지 포함해 프론트의 15초 타임아웃에 걸리는 경우도 있었습니다.

해결 — 입력이 같으면 결과도 같은 리포트성 응답만 골라 source | 모델 | 입력의 SHA-256 해시를 키로 DB에 캐싱하고, 실거래·학군 데이터가 천천히 바뀌는 점을 감안해 TTL을 7일로 두었습니다. 챗봇 대화처럼 맥락이 매번 다른 요청은 캐시 대상에서 제외했습니다. 추천 사유 생성에는 OpenAI 호출 타임아웃을 명시하고 프론트 타임아웃을 맞춰 조정했습니다.

효과 — 반복 조회되는 단지 리포트는 즉시 응답하게 되었고, 추천 결과 응답 시간을 약 4배 단축했습니다. 캐시 저장 실패는 응답을 막지 않도록 처리해 캐시 계층이 장애 지점이 되지 않게 했습니다.

소셜 로그인 계정 연결

문제 — Google과 Kakao는 프로필 응답 구조가 다르고, Kakao는 이메일 제공에 동의하지 않으면 이메일이 없어 이메일을 로그인 식별자로 쓰는 기존 User 모델과 충돌했습니다.

해결 — provider별 프로필 파싱을 분리하고, (provider, provider_id)를 복합 유니크로 하는 SocialAccount 모델로 소셜 계정과 내부 User를 연결했습니다. 이메일이 없는 경우 provider 기반 대체 이메일을 생성하고 username 충돌은 자동으로 회피하도록 했습니다. OAuth state를 세션에 저장·검증해 CSRF를 방지하고, 콜백에서 내부 JWT를 발급해 일반 로그인과 같은 세션 흐름을 타도록 했습니다.

효과 — 로그인 방식에 관계없이 이후 API는 동일한 JWT 인증을 사용하며, 같은 소셜 계정으로 재로그인해도 중복 계정이 생기지 않습니다.
