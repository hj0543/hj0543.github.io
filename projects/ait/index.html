실시간 AI 모의면접

목차요약배경주요 기능기여아키텍처ERD문제 해결협업링크

프로젝트 개요

Ait(AI Interview Trainer)는 개발자를 위한 AI 모의면접 & 면접 스터디 통합 플랫폼입니다. 지원자가 등록한 이력서·자기소개서·GitHub 저장소를 근거로 AI 면접관이 질문하고, 답변의 논리·표정·시선까지 분석해 리포트로 돌려줍니다. 여기에 LiveKit 기반 화상 스터디룸, 그룹톡, 자료실, 스터디원 상호 평가를 붙여 "혼자 연습 → 함께 점검 → 성장 확인"이 한 서비스 안에서 이어지도록 만들었습니다.

개발 배경 및 필요성

  • 기능의 파편화: 기존 면접 스터디는 모집, 연습, 평가, 커뮤니케이션이 각기 다른 도구에 흩어져 있어 운영 비용이 큽니다.
  • 기존 AI 모의면접의 한계: 이력서는 분석하지만 GitHub까지 연동해 실제 프로젝트 코드에 근거한 깊이 있는 질문을 던지는 서비스는 드뭅니다.
  • 면접 컨설팅의 한계: 비용과 예약·시간 제약 때문에 충분히 반복 연습하기 어렵습니다.

이 문제를 해결하기 위해 지원자의 개인 데이터를 반영하는 AI 면접관과 스터디 협업 기능을 결합한 Ait를 개발했습니다.

주요 기능

  • 개인화된 RAG 기반 질문 생성: 이력서, 자기소개서, GitHub 데이터를 기반으로 질문을 생성하며 면접 유형(기술·인성·CS)별로 참고 문서 비중을 다르게 적용합니다.
  • 동적 꼬리 질문 시스템: 루브릭 기준으로 답변을 채점하고 기준 미충족 시 꼬리 질문으로 이어갑니다.
  • 맞춤형 면접관 페르소나: 편안함·실전·압박 등 면접관 어조를 선택해 다양한 면접 환경을 훈련합니다.
  • 음성 기반 면접 진행: 질문은 TTS로 읽어 주고, 답변은 자동 녹음·STT로 받아 실제 면접처럼 말로 진행합니다.
  • 비언어 피드백: MediaPipe로 표정·시선을 캡처해 답변 내용과 함께 리포트에 반영합니다.
  • 실시간 화상 스터디룸: LiveKit 화상 세션, 화면 공유, STOMP 기반 그룹톡, 자료실, 스터디원 간 레이더 차트 평가를 제공합니다.
  • 성장 대시보드: 면접 회차별 점수 추이와 스터디 활동을 한눈에 확인합니다.

담당 역할 및 기여

프론트엔드 리더로서 공통 아키텍처와 디자인 시스템을 설계하고, 핵심 화면인 AI 면접과 화상 스터디를 구현했습니다.

  • 프론트엔드 아키텍처: Vite + React 19 + TypeScript 기반 프로젝트 구조, 라우팅과 인증 가드(ProtectedRoute), API 모듈 계층, OAuth(Google·GitHub) 흐름 설계
  • 디자인 시스템: Figma 가이드를 design-system.md와 CSS 토큰으로 옮기고 shadcn/ui를 Ait 토큰으로 재정의. 색상·간격·그림자·타이포·모션 규칙을 문서화해 팀 전체가 같은 기준으로 구현
  • 랜딩페이지: GSAP·Three.js 기반 진입 모션과 3D 연출
  • 대시보드: 면접 현황·스터디 현황 탭, 성장 추이 시각화
  • AI 모의면접: 5단계 설정 위저드 → 질문 생성 → 세션 진행(TTS·자동 녹음·STT·MediaPipe 캡처) → 분석 리포트까지 전 과정
  • 스터디 라운지: 스터디 탐색·신청·관리, LiveKit 화상 세션, 화면 공유, 그룹톡, 자료실, 상호 평가
  • 서류함: Tiptap 기반 이력서·자소서 에디터, 미저장 이탈 방지, DOMPurify sanitize
  • 실시간 알림: SSE 단일 연결을 여러 화면에 팬아웃하는 알림 스트림

시스템 아키텍처

ERD

기술적 고민 및 문제 해결

실시간 화상 세션의 복잡한 상태 관리

문제 — 참여자 입장·퇴장, 음소거, 화면 공유가 동시에 발생하면 화면과 실제 미디어 상태가 어긋났습니다. 컴포넌트가 자체 상태를 들고 있으면 LiveKit의 실제 트랙 상태와 이중으로 관리되는 문제도 있었습니다.

해결 — 모든 상태의 출처를 LiveKit 이벤트 한 곳으로 통일했습니다. Room 연결과 트랙 구독은 세션 컴포넌트가 소유하고 하위 트리에는 RoomContext로 내려주어, 카메라·마이크·화면 공유 트랙을 소스별로 분리해 구독하도록 구성했습니다.

효과 — 참여자 한 명이 입·퇴장하거나 마이크를 껐을 때 해당 타일만 갱신되고 나머지 화면은 영향을 받지 않게 되었습니다.

참여자 수와 화면 공유에 따라 달라지는 레이아웃

문제 — 참여자가 늘어날수록 영상이 과도하게 작아지고, 화면 공유가 시작되면 레이아웃이 흔들렸습니다. 단순히 CSS Grid의 열 수를 참여자 수에 따라 분기하는 방식은 4:3 영상 비율 때문에 레터박스 여백도 크게 남았습니다.

해결 — 가능한 모든 열 수를 순회하며 타일 하나의 실제 표시 면적이 최대가 되는 배치를 계산하도록 바꿨습니다. 컨테이너 크기와 참여자 수가 바뀔 때마다 최적 열 수를 다시 구하고, 뷰 상태를 그리드 / 특정 참여자 / 화면 공유 세 가지로 명시적으로 모델링했습니다.

효과 — 인원이 변해도 영상이 항상 가장 크게 보이며, 보고 있던 화면 공유가 종료되면 남은 공유 화면이나 그리드로 자동 복귀합니다.

MediaPipe 기반 비언어 데이터 캡처

문제 — AI 면접의 비언어적 피드백을 위해 MediaPipe FaceLandmarker로 표정·시선 데이터를 프레임 단위로 추출해야 했지만, 실시간 추론이 면접 화면 자체를 버벅이게 만들면 안 된다는 제약이 있었습니다.

해결 — 매 프레임 대신 5FPS로 샘플링하고 서버의 집계 주기와 맞춰 불필요한 연산과 전송을 줄였습니다. GPU 델리게이트로 먼저 시도하고 실패하면 CPU로 폴백했으며, 시선 이탈 가이드가 경계값 근처에서 깜빡이는 문제는 켜짐·꺼짐 임계값을 다르게 두는 히스테리시스로 해결했습니다. 임계값은 정면 응시와 대각선 응시를 직접 측정한 값을 기준으로 조정했습니다.

효과 — 저사양·구형 기기에서도 기능이 중단되지 않고 시선 이탈 안내가 안정적으로 동작합니다. 점수 계산은 서버와 AI 파트가 담당하고 프론트엔드는 캡처와 전송까지만 책임지도록 경계도 명확히 나눴습니다.

끊김 없는 음성 면접 흐름

문제 — 질문 TTS 재생 → 답변 녹음 시작 → STT 인식이 하나의 흐름으로 이어져야 했지만, 렌더 타이밍에 따라 녹음 시작 전에 빈 'idle' 화면이 잠깐 그려지거나 StrictMode에서 녹음이 두 번 시작되는 문제가 있었습니다. 서버 TTS가 실패하거나 브라우저 STT가 중간에 끊기면 면접이 멈추기도 했습니다.

해결 — 질문별 키를 기준으로 녹음 시작을 useLayoutEffect에서 한 번만 실행하도록 보장해 중간 화면 없이 바로 답변 단계로 넘어가게 했습니다. TTS는 서버 mp3 재생 실패 시 브라우저 음성 합성으로, STT는 세션 종료 시 자동 재시작으로 폴백을 두었습니다. 마이크 레벨 미터와 장치 점검 단계를 세션 진입 전에 배치해 장치 문제를 미리 걸러냈습니다.

효과 — 사용자가 버튼을 누르지 않아도 질문을 듣고 바로 답하는 실제 면접과 같은 리듬으로 진행되며, 외부 API 장애가 있어도 면접이 중단되지 않습니다.

협업 방식

  • Jira — 사용자 스토리 단위로 작업을 분리하고 담당자와 진행 상태를 관리했습니다.
  • Git — 티켓 단위 브랜치를 생성하고 Pull Request와 코드 리뷰를 거쳐 병합했습니다.
  • Notion — 회의록, 일정, 기획 내용, 공통 개발 규칙을 문서화했습니다.
  • API 명세서 — 프론트엔드와 백엔드가 요청·응답 형식을 함께 관리하고, 누락된 API는 api-gaps.md로 정리해 BE에 요청했습니다.
  • 프론트엔드 리딩 — Figma 가이드를 디자인 시스템 문서와 토큰으로 옮겨 raw hex·임의 간격 사용을 금지하는 규칙을 세웠고, shadcn/ui를 Ait 토큰으로 재정의해 팀원이 같은 컴포넌트로 일관된 화면을 만들 수 있게 했습니다. 도메인 규칙(domain-rules.md)과 BE 핸드오프 문서를 작성해 FE·BE 간 컨텍스트 공유를 맡았습니다.
