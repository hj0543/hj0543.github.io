21:T3a79,<h2 id="project-ait-section-0">프로젝트 개요</h2>
<p>**Ait(AI Interview Trainer)**는 개발자가 자신의 이력서·자기소개서·GitHub를 바탕으로 면접을 연습하고, 결과를 점검한 뒤 스터디에서 함께 준비하도록 만든 AI 면접 훈련 플랫폼입니다.</p>
<p>저는 6인 팀의 <strong>프론트엔드 리더</strong>로 참여했습니다. 평가 기준과 면접 진행·리포트 흐름을 설계하고, 음성·영상 정보를 다루는 AI 모의면접과 화상 스터디를 구현했습니다. 여러 사람이 같은 서비스를 만들 수 있도록 디자인과 면접 상태의 공통 기준을 문서화하고, 프론트엔드와 백엔드의 연동 요구사항도 정리했습니다.</p>
<h2 id="project-ait-section-1">문제 정의와 목표</h2>
<p>기획에서 주목한 문제는 <strong>연습을 시작하는 과정과 연습 결과를 다음 준비로 연결하는 과정이 끊겨 있다는 점</strong>이었습니다.</p>
<ul>
<li>이력서와 프로젝트 경험을 준비해도, 이를 바탕으로 질문받고 반복 연습할 환경이 필요했습니다.</li>
<li>답변을 반복하는 것만으로는 내용과 전달 방식 중 무엇을 보완해야 하는지 파악하기 어려웠습니다.</li>
<li>스터디 모집, 화상 면접, 자료 공유, 피드백이 서로 다른 도구에 흩어지면 준비와 운영에 추가 작업이 생겼습니다.</li>
</ul>
<p>이에 따라 **‘혼자 연습 → 결과 확인 → 함께 점검 → 다시 연습’**으로 이어지는 흐름을 목표로 삼았습니다. 개인 자료를 바탕으로 질문하고, 평가 기준에 따라 피드백을 정리하며, 같은 플랫폼에서 스터디 활동까지 이어지도록 구성했습니다.</p>
<h2 id="project-ait-section-2">핵심 기획 결정</h2>
<h3>1. 무엇을 개선해야 하는지 알 수 있도록 평가 기준부터 설계</h3>
<p>면접을 여러 번 진행하는 것과 자신의 부족한 점을 확인하는 것은 다른 문제였습니다. 저는 답변 내용, 직무 적합도, 전달력, 차별성을 아우르는 <strong>평가 기준</strong>을 설계하고, 결과를 평가 지표와 그래프로 확인할 수 있는 리포트를 기획했습니다.</p>
<p>질문별 피드백과 면접 회차별 추이를 연결해 사용자가 이번 답변에서 보완할 부분과 이전 연습과의 차이를 살펴보도록 했습니다. 평가 기준과 결과를 보여주는 흐름을 구체화하고, 실제 점수 계산은 서버·AI 파트가 담당하도록 역할을 나눴습니다.</p>
<h3>2. 음성과 영상 처리를 하나의 면접 경험으로 연결</h3>
<p>실제 면접처럼 질문을 듣고 말로 답하는 흐름을 만들기 위해 <strong>설정 → 장치 점검 → 질문 안내 → 답변 녹음·음성 인식 → 표정·시선 캡처 → 분석 리포트</strong>를 연결했습니다. 저는 이 과정을 프론트엔드에서 직접 구현했습니다.</p>
<p>기술을 각각 연결하는 것만으로는 부족했습니다. 질문이 끝난 뒤 답변을 시작하는 시점, 마이크가 정상적으로 동작하는지 확인하는 방법, 음성 안내나 인식이 끊겼을 때의 처리도 정해야 했습니다.</p>
<p>장치 점검과 마이크 레벨 표시를 면접 전에 배치하고, 음성 안내와 인식에는 대체 경로와 재시작 처리를 두었습니다. 표정·시선 캡처는 면접 진행에 영향을 덜 주도록 수집 주기를 조정했습니다. 프론트엔드는 데이터의 캡처·전송을 맡고 서버·AI 파트는 집계·평가를 맡도록 책임도 구분했습니다.</p>
<h3>3. 혼자 연습한 뒤 다른 사람과 점검할 수 있는 환경 구성</h3>
<p>AI 모의면접에 더해 스터디 탐색·신청·관리, 화상 세션, 화면 공유, 그룹톡, 자료실과 상호 평가를 연결했습니다. 개인 연습과 동료 피드백을 한 플랫폼에서 진행하도록 구성한 것입니다.</p>
<p>화상 스터디에서는 참여자 수와 화면 공유 여부에 따라 필요한 화면이 달랐습니다. 저는 그리드 보기, 특정 참여자 보기, 화면 공유 보기를 구분해 구현하고, 화면 공유가 끝나면 남은 공유 화면이나 그리드로 돌아가도록 했습니다. 사용자가 현재 점검하는 대상에 맞춰 화면을 볼 수 있게 하는 데 집중했습니다.</p>

<h2 id="project-ait-section-4">담당 역할과 협업</h2>
<p>제 역할은 면접과 스터디 화면을 구현하면서, 팀이 같은 기준으로 작업할 수 있도록 필요한 정보를 정리하는 것이었습니다.</p>
<ul>
<li><strong>평가와 이용 흐름:</strong> 평가 기준, 면접 진행 단계, 지표·그래프 리포트 기획</li>
<li><strong>공통 기준:</strong> Figma 가이드를 디자인 시스템 문서와 색상·간격·타이포 등 공통 값으로 옮기고, 면접 상태와 도메인 규칙 문서화</li>
<li><strong>프론트엔드 구현:</strong> AI 면접, 화상 스터디, 대시보드, 서류함, 알림 등 담당 화면과 공통 구조 구현</li>
<li><strong>연동 조율:</strong> API 명세와 화면을 대조해 누락 필드와 연동 대기 항목을 정리하고, 필요한 응답 형식을 백엔드에 요청</li>
<li><strong>결과 전달:</strong> 최종 발표 자료 제작과 시연 담당</li>
</ul>
<p>예를 들어 스터디 목록에 현재 인원수 필드가 없을 때는 기존 응답으로 표시할 수 있는 정원을 먼저 보여주고, 추가로 필요한 필드를 요청했습니다. 연동 요청도 ‘무엇이 안 되는지’와 함께 ‘어디까지 확인했고 무엇이 더 필요한지’를 문서로 전달했습니다.</p>
<p>Jira의 작업 단위와 Git의 티켓별 브랜치·리뷰, Notion의 회의·기획 기록을 활용했습니다. 디자인과 도메인 규칙은 AI 코딩 에이전트를 사용할 때도 공통 기준으로 전달했습니다.</p>
<h2 id="project-ait-section-5">결과와 검증 범위</h2>
<ul>
<li><strong>구현 결과:</strong> 개인 자료를 바탕으로 한 AI 면접과 분석 리포트, 화상 스터디·상호 평가, 대시보드를 연결</li>
<li><strong>본인 기여:</strong> 평가 기준·진행 흐름 설계와 주요 프론트엔드 구현, 디자인·상태 기준과 API 연동 요청 문서화</li>
<li><strong>발표 결과:</strong> 최종 발표 자료를 제작하고 서비스를 시연</li>
</ul>
<p>평가 기준과 화면을 구현한 뒤에는 사용자가 그 결과를 이해하고 다음 연습에 활용할 수 있는지 확인하는 과정이 필요합니다. 다음 단계에서는 리포트를 보고 보완할 행동을 선택하는지, 표정·시선 지표의 의미를 적절히 이해하는지, 면접 설정과 장치 점검에서 막히는 부분이 있는지를 검증하고 싶습니다.</p>
<p>프로젝트 후반에 연동과 검증 작업이 몰린 점도 과제로 남았습니다. 다음에는 화면 구현과 함께 연동 확인·수정 시간을 일정에 포함하고, 역할별 완료 기준을 더 일찍 공유하려고 합니다.</p>

<h4>실시간 화상 세션의 복잡한 상태 관리</h4>
<p><strong>문제</strong> — 참여자 입장·퇴장, 음소거, 화면 공유가 동시에 발생하면 화면과 실제 미디어 상태가 어긋났습니다. 컴포넌트가 자체 상태를 들고 있으면 LiveKit의 실제 트랙 상태와 이중으로 관리되는 문제도 있었습니다.</p>
<p><strong>해결</strong> — 모든 상태의 출처를 LiveKit 이벤트 한 곳으로 통일했습니다. Room 연결과 트랙 구독은 세션 컴포넌트가 소유하고 하위 트리에는 <code>RoomContext</code>로 내려주어, 카메라·마이크·화면 공유 트랙을 소스별로 분리해 구독하도록 구성했습니다.</p>
<p><strong>효과</strong> — 참여자 한 명이 입·퇴장하거나 마이크를 껐을 때 해당 타일만 갱신되고 나머지 화면은 영향을 받지 않게 되었습니다.</p>
<h4>참여자 수와 화면 공유에 따라 달라지는 레이아웃</h4>
<p><strong>문제</strong> — 참여자가 늘어날수록 영상이 과도하게 작아지고, 화면 공유가 시작되면 레이아웃이 흔들렸습니다. 단순히 CSS Grid의 열 수를 참여자 수에 따라 분기하는 방식은 4:3 영상 비율 때문에 레터박스 여백도 크게 남았습니다.</p>
<p><strong>해결</strong> — 가능한 모든 열 수를 순회하며 타일 하나의 실제 표시 면적이 최대가 되는 배치를 계산하도록 바꿨습니다. 컨테이너 크기와 참여자 수가 바뀔 때마다 최적 열 수를 다시 구하고, 뷰 상태를 그리드 / 특정 참여자 / 화면 공유 세 가지로 명시적으로 모델링했습니다.</p>
<p><strong>효과</strong> — 인원이 변해도 영상이 항상 가장 크게 보이며, 보고 있던 화면 공유가 종료되면 남은 공유 화면이나 그리드로 자동 복귀합니다.</p>
<h4>MediaPipe 기반 비언어 데이터 캡처</h4>
<p><strong>문제</strong> — AI 면접의 비언어적 피드백을 위해 MediaPipe FaceLandmarker로 표정·시선 데이터를 프레임 단위로 추출해야 했지만, 실시간 추론이 면접 화면 자체를 버벅이게 만들면 안 된다는 제약이 있었습니다.</p>
<p><strong>해결</strong> — 매 프레임 대신 5FPS로 샘플링하고 서버의 집계 주기와 맞춰 불필요한 연산과 전송을 줄였습니다. GPU 델리게이트로 먼저 시도하고 실패하면 CPU로 폴백했으며, 시선 이탈 가이드가 경계값 근처에서 깜빡이는 문제는 켜짐·꺼짐 임계값을 다르게 두는 히스테리시스로 해결했습니다. 임계값은 정면 응시와 대각선 응시를 직접 측정한 값을 기준으로 조정했습니다.</p>
<p><strong>효과</strong> — 저사양·구형 기기에서도 기능이 중단되지 않고 시선 이탈 안내가 안정적으로 동작합니다. 점수 계산은 서버와 AI 파트가 담당하고 프론트엔드는 캡처와 전송까지만 책임지도록 경계도 명확히 나눴습니다.</p>
<h4>끊김 없는 음성 면접 흐름</h4>
<p><strong>문제</strong> — 질문 TTS 재생 → 답변 녹음 시작 → STT 인식이 하나의 흐름으로 이어져야 했지만, 렌더 타이밍에 따라 녹음 시작 전에 빈 &#39;idle&#39; 화면이 잠깐 그려지거나 StrictMode에서 녹음이 두 번 시작되는 문제가 있었습니다. 서버 TTS가 실패하거나 브라우저 STT가 중간에 끊기면 면접이 멈추기도 했습니다.</p>
<p><strong>해결</strong> — 질문별 키를 기준으로 녹음 시작을 <code>useLayoutEffect</code>에서 한 번만 실행하도록 보장해 중간 화면 없이 바로 답변 단계로 넘어가게 했습니다. TTS는 서버 mp3 재생 실패 시 브라우저 음성 합성으로, STT는 세션 종료 시 자동 재시작으로 폴백을 두었습니다. 마이크 레벨 미터와 장치 점검 단계를 세션 진입 전에 배치해 장치 문제를 미리 걸러냈습니다.</p>
<p><strong>효과</strong> — 사용자가 버튼을 누르지 않아도 질문을 듣고 바로 답하는 실제 면접과 같은 리듬으로 진행되며, 외부 API 장애가 있어도 면접이 중단되지 않습니다.</p>
