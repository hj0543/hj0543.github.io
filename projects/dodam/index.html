프로젝트 개요

오늘 무엇을 바꾸면, 내 목표를 더 빨리 이룰 수 있을까?

도담은 금융 목표를 가진 청년이 자신의 금융 상태를 진단하고, 소비·저축·대출 조건을 바꿨을 때 목표 달성 시점이 어떻게 달라지는지 비교하도록 돕는 개인 금융 코치 앱입니다.

저는 팀장·PM과 백엔드 개발을 맡았습니다. 중간발표 피드백을 계기로 서비스의 핵심 가치를 다시 정의하고, 진단·추천·시뮬레이션을 연결하는 흐름과 AI 코치의 응답 기준, 목표별 자금 배정 구조를 구체화했습니다. 줄어든 팀 인원에 맞춰 일정과 선행 작업도 조율했습니다.

SSAFY 교육용 금융망을 활용해 구현했으며, **특화 프로젝트 우수상(2등)**을 받았습니다.

기획 산출물

  • 요구사항 정의서

문제 정의와 목표

기획의 출발점은 금융 정보를 확인하는 것과 다음 행동을 결정하는 것 사이의 간격이었습니다. 소비내역과 계좌 잔액을 확인해도 다음 질문에 답하려면 사용자가 여러 정보를 직접 연결해야 했습니다.

  • 지금의 소비와 저축 방식으로 목표를 언제 달성할 수 있는가?
  • 소비 줄이기, 저축액 변경, 대출 상환 중 무엇부터 검토해야 하는가?
  • 각 선택이 목표 달성일과 당장의 생활비에 어떤 영향을 주는가?

따라서 서비스의 목표를 목표를 기준으로 문제를 찾고, 행동별 효과를 비교한 뒤, 실행과 변화 확인으로 이어지게 하는 것으로 정했습니다. 이 질문을 진단 항목과 기능 우선순위, 시연 흐름을 정하는 기준으로 삼았습니다.

핵심 기획 결정

1. 기능 목록을 목표 달성 중심의 흐름으로 재구성

중간발표에서 기존 가계부와 차별점이 부족하고, 기능이 많으며, AI 활용도가 낮다는 피드백을 받았습니다. 저는 서비스의 핵심 가치를 ‘얼마를 썼는지 보여주는 가계부’에서 **‘소비를 어떻게 바꾸면 목표 달성일을 앞당길 수 있는지 알려주는 금융 코치’**로 다시 정의했습니다.

이 기준으로 기능의 우선순위를 정리하고, 진단 결과에서 개선 행동을 확인한 뒤 같은 조건의 시뮬레이션으로 효과를 비교하도록 연결했습니다. 발표도 사용자가 어떤 문제를 발견하고 어떤 선택을 하게 되는지를 중심으로 구성했습니다.

2. 자연어 질문의 편의성과 계산 결과의 일관성을 함께 설계

‘대출을 100만 원 먼저 갚으면 여행 목표를 언제 이룰 수 있을까?’라는 질문에 답하려면 사용자는 시뮬레이션 유형, 대출, 금액, 목표를 차례로 선택해야 했습니다. 이 단계를 줄이기 위해 대화형 AI 코치 토리에 서버의 계산 도구를 연결했습니다.

잘못된 수치가 금융 판단에 영향을 줄 수 있어, 질문의 의도 파악과 설명은 AI가, 계산은 서버가 담당하도록 경계를 정했습니다. 민감정보 입력은 차단하고, 응답에 계산 근거에 없는 숫자가 포함되면 안내 문장으로 대체했습니다. 화면과 대화가 같은 계산 결과를 사용하도록 한 것도 이 원칙에 따른 결정입니다.

제가 직접 맡은 구현에는 진단·추천·시뮬레이션 엔진과 토리의 소비 예측 조회, 대출 추가 상환 관련 도구가 포함됩니다.

3. 예측이 어려운 원인을 자금 관리 구조에서 해결

처음에는 목표마다 계좌를 연결해 저축 속도를 계산했습니다. 하지만 입출금 계좌에는 생활비와 저축액이 섞여 있어 잔액 변화가 목표 저축을 대표하지 못했고, 예측 모델을 적용해도 목표를 위해 실제로 쌓이는 금액을 구분하기 어려웠습니다. 목표가 늘 때마다 계좌를 추가로 준비해야 하는 부담도 있었습니다.

저는 전용 계좌 하나 안에서 목표별 금액을 나누는 세이프박스 구조를 제안하고 설계·구현했습니다. 외부 계좌와 도담 계좌 사이의 이동은 교육용 금융망 이체로, 목표별 담기·꺼내기는 내부 배정 기록으로 구분했습니다. 이 배정 원장을 기준으로 목표별 확보액과 저축 속도를 집계하도록 바꿨습니다.

이를 통해 사용자는 계좌 하나에서 여러 목표의 금액을 관리하고, 서비스는 생활비와 분리된 목표별 자금 흐름으로 진행률과 예상 달성일을 계산할 수 있게 했습니다.

사용자 흐름과 서비스 정책

기능 사이의 판단 기준과 수치가 이어지는 것을 중요하게 봤습니다. 추천은 진단 당시의 데이터 스냅샷을 기준으로 만들고, 그 추천을 같은 조건의 시뮬레이션으로 실행하도록 연결했습니다. 소비 예측은 예상액뿐 아니라 80% 예상 범위와 계산 근거(수준·추세·계절)를 함께 전달하도록 구성했습니다. 또래 비교는 비슷한 사용자 집단의 항목별 사분위 범위(25%~75%, 가운데 50%)를 일반적인 범위로 두고, 중앙값과 함께 보여주며 이 범위를 벗어난 항목을 또래와 다른 소비로 알려줍니다.

담당 역할과 협업

6명으로 시작한 팀에서 한 명이 취업하면서 5명이 개발을 이어갔습니다. 저는 최종 발표일부터 부하 테스트·QA·버그 수정 일정을 역산하고, Jira 이슈마다 담당자와 선행 작업을 정리했습니다. API 명세 변경은 관련 담당자에게 바로 공유하고, 제가 맡은 개발에서는 다른 팀원이 기다리는 선행 작업을 먼저 처리했습니다.

  • 기획과 범위: 문제 정의, 타깃, MVP 범위, 진단 기준, 효과 측정 기준을 담은 기획안 작성 주도
  • 업무 조율: 22개 도메인의 API 명세와 ERD를 기준으로 프론트엔드·백엔드 작업 범위와 연동 현황 관리
  • 설계·구현: 진단·추천·시뮬레이션 흐름, 소비·현금흐름 예측, 세이프박스, AI 코치 도구 구현
  • 품질과 전달: 시연 계정 데이터와 사용자 시나리오 설계, 화면별 QA, README·포팅 매뉴얼 등 최종 산출물 정리

이 과정을 통해 팀원들이 서로의 일정을 확인하고 먼저 조율을 요청하는 흐름이 생겼습니다. 최종 발표에서는 세이프박스와 목표 달성 시점 비교를 중심으로 서비스의 가치를 설명하고, 나머지 구현 상세는 시연과 질의응답으로 전달했습니다.

결과와 검증 범위

  • 프로젝트 성과: 계획한 일정을 지켜 본선에 진출하고 SSAFY 특화 프로젝트 우수상(2등) 수상
  • 구현 결과: 목표 설정·진단·행동 비교·AI 상담·금액 배정으로 이어지는 흐름 구현
  • 기술 검증: 팀 부하 테스트와 성능 개선, 백엔드 테스트 수행. 조건과 수치는 아래 구현 상세에 정리

시연과 기술 검증으로 서비스 흐름의 동작을 확인했습니다. 실제 사용자의 금융 행동 변화나 목표 달성 효과는 별도의 검증이 필요합니다. 다음 단계에서는 사용자가 진단에서 비교할 행동을 찾는지, 화면과 AI 설명을 같은 의미로 이해하는지, 생활비와 목표별 배정액을 구분할 수 있는지를 확인하고 싶습니다.

구현 상세와 기술 검증

담당 구현 범위, 시스템 구조, 기술적 문제 해결과 팀 검증 결과 펼치기

담당 구현 범위

  • 전체 212개 REST API 중 118개 구현 — Product, Card, Installment, Loan, Minus Account, Deposit/Savings, Cashflow, Diagnosis, Recommendation, Simulation 10개 도메인
  • 진단 → 추천 → 시뮬레이션으로 이어지는 핵심 코칭 파이프라인 설계 및 구현
    • 진단: 규칙 버전 기반 결과 캐시, 사용자 단위 실행 직렬화, 입력 스냅샷 보존, 목표 영향·이전 진단 대비 변화 API
    • 추천: 진단 스냅샷만 읽는 순수 함수형 생성기 3종, 위험도·효과·목표 기여도·시급성 기준 우선순위 점수, 수락·거절·완료·보류 상태 이력
    • 시뮬레이션: 10종 시나리오 계산기 + 복합 시나리오, 목표 달성일 투영, 추천 → 시뮬레이션 프리셋 연결
  • 시계열 소비 예측 설계·구현: 감쇠 추세 방식(수준 지수평활 + Theil-Sen 추세) 기반 월 변동 소비 예측 API와 리포트 예측 카드, 예측값의 성분별 분해(수준·추세 효과·계절 효과)와 작년 같은 달 실적 제공
  • 세이프박스(도담 계좌) 설계·구현(BE + FE): 전용 계좌 개설, 목표별 배정 원장, 금융망 실이체, 목표 생성·상세·자산 화면 전환
  • AI 코치(토리) 도구 추가: 소비 예측 조회 도구, 대출 추가상환 시 다음 납입액 변화 답변
  • 일 단위 현금흐름 예측 엔진과 잔액 부족 위험 탐지, 대출 이자 예측(원금균등·원리금균등·만기일시)·상환 부담률·금리 비교, 금융 효율 점수 계산
  • 카드번호·계좌번호 HMAC 해시 조회 및 마스킹 응답, 공통 조회 기간 정책(QueryPeriodPolicy) 설계
  • 시연 계정 24개월 거래 seed와 사용자 스토리 설계, 담당 도메인 구현 기준 문서 40여 건 작성(backend/docs/)

시스템 아키텍처

  • Client(React Native / Expo) → Nginx(TLS, 레이트 리밋, 보안 헤더) → Spring Boot API 서버 → MySQL 8.0 / Redis 7
  • 외부 연동: SSAFY 교육용 금융망 API(계좌·거래·이체·신용등급), SSAFY GMS(OpenAI gpt-5.4-mini 중계), 카카오/구글 소셜 로그인, Firebase Cloud Messaging
  • 배포: AWS EC2 1대 + Docker Compose / GitLab 웹훅 → Jenkins 빌드·테스트·배포·헬스체크 자동화 / Let's Encrypt 자동 갱신
  • 모니터링: Prometheus·Grafana(지표), Loki·Promtail(로그), cAdvisor, Mattermost 알림

ERD

도메인은 크게 다섯 묶음으로 나뉩니다.

  • 사용자·연동: user, financial_profile, 금융망 연결
  • 금융 데이터: account, transaction, card, installment, loan, 마이너스통장, deposit/savings, 구독
  • 목표: goal, goal_account(목표별 확보액), goal_history, safebox_account, safebox_movement
  • 분석: cashflow_forecast, cashflow_risk, diagnosis, diagnosis_issue, recommendation
  • 시뮬레이션·상품: simulation, simulation_scenario, simulation_goal_impact, product

스키마는 Flyway 마이그레이션으로 관리했고, 진단·추천·시뮬레이션 결과는 계산 당시의 입력을 JSON 스냅샷으로 함께 저장해 나중에도 같은 결과를 재현할 수 있도록 했습니다.

기술적 고민 및 문제 해결

1. 서버 계산과 숫자 검증으로 오류를 줄인 AI 코치

  • 문제: 금융에서 AI 환각은 허용될 수 없음. LLM이 금리·기간을 직접 계산하면 그럴듯하지만 틀린 숫자가 사용자에게 전달됨
  • 해결: LLM에게는 도구 선택과 문장 생성만 맡기고 계산은 전부 서버 엔진이 수행
    • 입력 가드에서 계좌·카드번호·이메일 등 민감정보 차단 → LLM 1차 호출로 도구 8종(소비 절감·저축액 변경·중도상환·대환·복합 시뮬레이션, 목표 달성 예측·최신 진단·소비 예측 조회) 중 선택. ID·계좌번호는 인자로 받지 않음
    • 서버의 진단·추천·K-Means·시계열·시뮬레이션 엔진이 계산한 facts만 LLM 2차 호출에 전달해 3문장·200자 이내로 설명
    • 출력 가드가 facts에 없는 숫자를 발견하면 템플릿 문장으로 대체, LLM 장애 시에도 응답
  • 효과: 화면의 숫자는 facts에서만 나오고, LLM은 검증된 계산 결과를 쉬운 말로 설명하는 역할로 한정됨

2. 시계열 소비 예측 — 학습 없이 서버에서 즉시 계산

  • 문제: "다음 달 얼마나 쓸까"를 보여주고 싶지만 사용자별 이력이 짧고, 여행·이사 같은 일회성 지출이 섞여 있으며, 별도 학습 서버를 둘 여유가 없음
  • 해결: 월 단위 감쇠 추세 방식 채택 — 수준은 지수평활, 추세는 Theil-Sen으로 추정하고 먼 달로 갈수록 추세를 감쇠
    • 이상치 정리: 중앙값에서 MAD × 1.4826 × 3 이상 벗어난 달은 잘라 일회성 지출 영향 제거
    • 수준 α = 0.5: 한 달 튄 소비에 과민 반응하지 않음 / 추세 감쇠 φ = 0.85: "계속 늘어난다"는 과장 예측 방지
    • 예측 구간 Z = 1.28: 잔차 표준편차와 정규분포 계수로 80% 예상 범위를 내고 예측 시점(h)이 멀수록 √h만큼 넓혀, 숫자 하나가 아닌 범위로 불확실성까지 전달
    • 이력 3개월 이상이면 수준 + 추세, 12개월 이상이면 명절·연말 계절성(승법 계절지수)까지 반영
    • 거래가 없던 달은 0이 아니라 결측으로 처리 — 0을 넣으면 수준이 끌려 내려가 휴면 구간이 있는 사용자의 예측이 절반 이하로 떨어짐
  • 효과: 수준 + 추세분 + 계절분 = 예상액이 원 단위로 정확히 성립하도록 응답을 시계열 성분별로 분해해, 리포트 카드와 AI 코치가 같은 근거를 그대로 보여줌

3. 목표별 계좌 연동 → 도담 계좌 + 세이프박스로 방향 전환

  • 문제: 처음에는 목표 하나에 여러 계좌를 연결해 저축 속도를 계산했음. 예적금은 매달 일정하지만 입출금 계좌는 소비와 섞여 금액이 불규칙했고, 앞의 시계열 모델을 적용해 봐도 예측 구간이 끝없이 벌어져 저축 속도를 예측할 수 없었음. 목표가 늘수록 입출금 계좌도 여러 개 새로 만들어야 했음
  • 해결: 사용자당 도담 전용 계좌 하나를 금융망에 개설하고, 목표별 금액은 계좌 안의 세이프박스에 나눠 담는 구조로 전환. 기존 계좌 ↔ 도담 계좌 이동만 실제 이체이고, 담기·꺼내기는 목표별 배정 원장(safebox_movement)에 기록하는 내부 배정. 저축 속도는 이 원장의 최근 완료 월 순증감으로 계산
    • 배정 합계를 넘는 출금은 409로 차단, 사용자 행 잠금으로 배정·출금·동기화를 직렬화
    • 금융망 계좌 개설 전에 시도 기록을 별도 트랜잭션으로 남겨, 타임아웃처럼 결과가 불명확한 경우 중복 개설을 막음
  • 효과: 계좌는 하나로 유지하면서 목표별 진행률과 예상 달성일을 안정적으로 계산할 수 있게 됨

4. 시뮬레이션 중복 실행 방지와 재현성

  • 문제: 같은 조건으로 여러 번 실행하면 결과 행이 쌓이고, 상품 금리가 바뀌면 같은 요청도 다른 결과가 나와 이전 결과와 비교할 수 없음. 요청 파라미터가 JSON이라 DB UNIQUE로 막을 수 없음
  • 해결: (userId, type, 표준 형식으로 변환한 입력 지문, 기준일, 계산 버전)의 SHA-256 요청 해시를 저장해 같은 날 같은 지문이면 기존 건을 반환(200), 새 조건이면 생성(201). 동시 요청은 사용자 행 PESSIMISTIC_WRITE 잠금으로 직렬화. 계산식이 바뀌면 계산 버전을 올려 이전 결과를 재사용하지 않음
  • 효과: before/after 스냅샷이 보존되어 조건 변경 전후 비교가 가능하고, 복합 시나리오 자식 9종의 순서를 바꿔도 집계 결과가 같음을 통합 테스트로 고정

5. 진단 → 추천 → 시뮬레이션 간 계산 일관성

  • 문제: 추천이 제시한 효과(예: 월 20만 원 절감)와 실제 시뮬레이션 결과가 다르면 서비스를 신뢰할 수 없음
  • 해결: 추천 생성기가 현재 데이터를 재계산하지 않고 진단이 저장한 스냅샷만 읽도록 순수 함수로 설계. 추천 응답에 시뮬레이션 프리셋(엔드포인트 + 요청 본문)을 포함해 클릭 한 번으로 같은 값을 실행. 추천 효과 = 시뮬레이션 after − before 등식을 API 수준 테스트로 고정하고, 예상 달성일은 목표 도메인과 같은 식·같은 기준일로 계산
  • 효과: 규칙 버전을 명시해 규칙 변경 시 캐시 재사용 범위가 분리됨

6. 현금흐름 위험 판정 시점

  • 문제: 하루 마감 잔액으로 판정하면 여러 출금 중 어느 건에서 막히는지 알 수 없고, 한 번 음수가 되면 이후 날짜가 전부 위험으로 잡힘
  • 해결: 하루 안에서 입금을 먼저 반영한 뒤 각 출금 직전 잔액으로 판정. 탐지를 잔액 순회 계산기 안에서 함께 수행해 입출금 반영 순서가 두 곳으로 갈라지지 않도록 함
  • 효과: 위험이 "어느 날 어떤 출금에서 얼마 부족"으로 특정되어 진단·추천의 입력으로 그대로 연결

7. 민감한 금융 정보 보호

  • 문제: 카드번호·계좌번호를 조회 키로 써야 하지만 원문 저장·단순 해시는 유출 시 복원 가능
  • 해결: 암호화 키와 분리된 키를 쓰는 HMAC-SHA-256 해시 컬럼으로 조회, 원문은 AES-256-GCM(매번 새 IV)으로 암호화, 응답은 마스킹 값만 제공. 모든 리소스 조회에 소유권 조건을 넣고, 타인 리소스는 존재 여부를 노출하지 않도록 404 처리
  • 효과: 응답·로그·시뮬레이션 스냅샷 어디에도 원문·해시가 남지 않음을 테스트로 검증

팀 기술 검증 결과

  • 부하 테스트(팀): k6로 로그인 → 계좌 → 카드 → 대출 → 진단 → 추천 실제 사용자 흐름을 재현해 100만 요청 오류율 0.00%, 지속 처리량 약 796 req/s, 22분 연속 부하에서 메모리·커넥션 누수 없음 (24개월·139만 건 거래 데이터 기준)
  • 성능 개선(팀): JFR 프로파일링으로 병목을 찾아 DB Prepared Statement 캐시 활성화와 미사용 보안 필터 계측 비활성화, 설정 2줄·Java 코드 변경 0줄로 화면 흐름 p95를 2.01초 → 1.47초(−27%)로 단축
  • 품질: 백엔드 테스트 1,100여 건(H2 통합 + MySQL 전용 제약 검증), develop 머지 시 자동 빌드·테스트·헬스체크
