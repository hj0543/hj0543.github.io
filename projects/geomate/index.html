슬라이더로 돌려 보는 회전체

목차요약문제 정의와 목표핵심 기획 결정사용자 흐름담당 역할과 협업결과와 검증 범위구현 상세관련 글과 링크

프로젝트 개요

종이 위에서는 돌릴 수도, 자를 수도 없습니다.

**GEOMATE(지오메이트)**는 학생이 자기 문제의 도형을 태블릿에서 직접 돌리고, 접고, 자르면서 스스로 답을 찾도록 돕는 2D·3D 기하 학습 앱입니다. 문제 사진 한 장을 조작 가능한 도형으로 바꾸고, 답을 알려 주는 대신 먼저 예측하고 진단과 힌트로 다시 시도하게 합니다.

수학학원에서 학생을 지도하던 경험에서 출발해, SSAFY 자율 프로젝트에서 6인 팀으로 한 달 동안 개발했습니다. 저는 PM·프론트엔드·AI를 맡아 문제 정의와 학습 흐름, 화면 기준을 정하고, 학생이 문제를 푸는 도형 조작 공간과 S펜 조작, 사진 해석과 인식 모델을 개발했습니다. 최종 발표도 맡았습니다.

갤럭시탭 앱으로 원스토어에 출시했고, 발표 시점 다운로드는 148회입니다.

문제 정의와 목표

학원에서는 공식을 알고 있어도 도형 속 관계를 찾지 못해 풀이를 시작하지 못하는 학생이 많았습니다. 입체 문제에서는 평면 그림만 보고 가려진 면이나 단면, 전개도를 머릿속으로 떠올려야 했습니다.

자체 설문(2026년 10월 16일 기준 94명)에서 중등 수학에서 가장 어려운 영역으로 도형을 고른 응답이 37%로 가장 많았습니다. 도형이 어려운 이유로는 어디서부터 풀지 모른다가 가장 많았습니다.

필요한 기능으로는 사진 속 도형을 직접 조작(50.6%), 그린 선·식의 잘못된 부분 확인(34.8%), 막힌 단계에서 다음 힌트(34.8%)를 꼽았습니다. 그래서 목표를 세 가지로 정했습니다.

  • 내 문제의 도형을 손으로 만질 수 있게 한다.
  • 어디서 틀렸는지 진단하고, 막히면 다음에 볼 곳을 알려 준다.
  • 답은 학생이 스스로 생각한 뒤에만 보여 준다.

대상은 도형 감각을 잡아야 하는 초5 ~ 중3입니다. 기존 도구(GeoGebra, 알지오매스)는 도형을 처음부터 직접 작도해야 하고 막힌 단계의 진단·힌트가 없어, 도형을 만드는 도구를 넘어 내 문제를 푸는 학습까지 잇는 것을 차별점으로 삼았습니다.

핵심 기획 결정

1. 답은 엔진이 계산하고, AI는 읽기와 설명만

문제 사진은 VLM이 읽어 계산 엔진이 이해하는 요청으로 옮깁니다. 값마다 읽음·추론·못 읽음을 표시해, 사진에서 확인하지 못한 값을 그럴듯하게 채우지 않게 했습니다. 서버의 Python 엔진이 요청을 검사해 그림에 없는 점처럼 계산할 수 없는 부분을 찾으면, 이유를 붙여 한 번 다시 요청합니다.

정답은 AI가 아니라 엔진이 계산합니다. 조작에 즉시 반응해야 하는 앱에는 TypeScript 엔진을, 최종 판정에는 서버의 Python 엔진을 쓰고, 같은 입력 451개로 두 엔진의 결과가 같은지 교차 검증했습니다.

2. 힌트는 방향만, 정답은 ‘결과 확인’ 뒤에

힌트는 엔진이 정한 풀이 순서를 LLM이 질문과 단계 문장으로 바꾼 것입니다. 만든 힌트도 그대로 내보내지 않고, 정답이 드러나면 탈락시킵니다.

화면에서도 같은 기준을 적용했습니다. 팀 예제 71개를 태블릿에서 하나씩 열어 보며 힌트의 계산 값, 처음부터 다 돌아간 회전체처럼 학생이 생각하기 전에 답을 보여 주는 곳을 찾아 결과 확인 뒤로 옮겼습니다.

3. 펜 하나로 쓰고, 지우고, 돌리기

학교에 보급된 갤럭시탭과 S펜을 기준으로 했습니다. 처음에는 조작은 손, 필기는 펜으로 나눴지만, S펜 옆 버튼을 누른 채 시작한 자리에 따라 선 위에서는 지우개, 입체 위에서는 회전·접기, 빈 곳에서는 화면 이동이 되도록 바꿨습니다. 펜을 내려놓지 않고 풀이를 이어 갈 수 있습니다.

사용자 흐름

혼자 학습: 문제 가져오기(사진·PDF) → 도형 복원 → 예측 → 진단 → 힌트 → 정답과 풀이 확인 → 학습 기록

클래스: 선생님이 퀘스트 배포 → 학생이 예측·진단·확인 → 선생님이 학생별 풀이 현황 확인 → 질문 답변

질문 답변에서는 풀이를 영상 대신 조작 기록으로 주고받습니다. 용량이 작고, 상대의 풀이를 재생하거나 그 상태에서 이어 풀 수 있습니다.

교재 문항은 서비스에 직접 넣지 않고, 예제와 튜토리얼은 팀이 만든 문항으로 구성했습니다. 학생이 찍은 사진은 본인 학습에만 사용합니다.

담당 역할과 협업

  • PM: 설문과 현장 경험을 문제 정의에 연결하고, ‘묻는 것에만 답한다·스스로 찾게 한다·손으로 직접·도형 공간이 주인공’이라는 화면 판단 기준을 정했습니다.
  • 프론트엔드: 도형 조작 공간의 배치를 네 차례 바꿔 도형이 놓일 공간을 넓히고, S펜·손가락 조작, 입체 위 필기, 답 입력, 나갔다 들어와도 이어 푸는 기능을 구현했습니다.
  • AI: 사진 해석 모델을 같은 사진으로 비교해 고르고, 문제 영역 보정과 손글씨 답 인식 모델을 직접 라벨링·학습했습니다.
  • 발표: 최종 발표를 맡아 문제 정의부터 핵심 기술, 트러블슈팅, 실사용 후기까지 전달했습니다.

정확도는 각 평가 세트 기준이고, 반응 속도는 개발 모드에서 측정했습니다. 수학과 교수님·현직 선생님 인터뷰와 원스토어 후기로 반응을 확인했지만, 학습 효과(성적 변화)는 정량으로 검증하지 못했습니다. 다음 단계에서는 같은 유형 문제의 사용 전후 정답률을 비교하고, 우연히 맞힌 답을 이유 설명이나 조건을 바꾼 유사 문제로 구분하려고 합니다.

구현 상세

시스템 구조와 기술적 문제 해결 펼치기

시스템 아키텍처

앱과 관리자 웹은 Spring Boot API를 쓰고, Spring이 Python 내부 서비스에 계산·판정·AI 작업을 요청합니다. 앱 안의 TypeScript 엔진은 도형 표시와 조작을 맡습니다.

기술적 고민 및 문제 해결

1. 더 작은 모델로 바꿀 수 있을까

미세조정 전에 더 작은 모델이나 낮은 추론 설정으로 충분한지 먼저 확인했습니다. 같은 사진으로 비교한 결과 작은 모델은 정답 11/20, 엔진 통과 12/20으로 크게 떨어져, 정확도가 가장 높은 GPT-6.1 Sol(medium)을 유지했습니다.

2. 문제 영역을 대충 골라도 맞춰 주기

사진에서 문제 영역을 고를 때 사각형이 조금 엇나가면 다시 맞춰야 했습니다. PP-DocLayout-S 기본 모델은 문제 영역을 제대로 잡지 못해, 문제·그림·보기를 한 영역으로 보는 기준으로 페이지를 직접 라벨링했습니다. 같은 교재가 학습과 검증에 섞이지 않게 교재 단위로 나눴습니다.

3. 수식 손글씨 답 인식

삼성 손글씨는 3/4를 314로, Google ML Kit는 4π를 44로 읽었습니다. 같은 S펜 표본으로 후보를 비교해 수식 전용 Uni-MuMER를 골랐고, 쓰는 사람에 따라 정확도가 64~87%로 갈려 여러 팀원의 글씨로 다시 학습했습니다. 이름을 쓰는 칸은 엔진이 아는 답 형식으로 구분해 ML Kit에 맡기고, 인식 결과를 칸 아래에 바로 보여 줘 다르면 다시 쓰게 했습니다.

4. 끊기는 조작을 측정해서 고치기

체감으로 짐작한 원인이 두 번 틀렸습니다. 끊긴 프레임과 다시 그린 횟수를 재 보니, 손으로 계속 바꾸는 값이 화면 전체 상태에 있어 값마다 툴바·카드·도형을 모두 다시 그린 것이 원인이었습니다. 움직이는 부분만 다시 그리고, 손을 따라 움직이는 그림은 UI 스레드에서 그리도록 바꿨습니다.

5. S펜 인식 영역

입체 영역을 화면 사각형으로 잡자 십자 전개도의 빈 모서리에서도 입체가 돌아갔습니다. 면마다 꼭짓점을 화면에 투영한 다각형으로 판정하고, 옆 버튼을 누르는 동안 인식 영역의 외곽선을 보여 줘 펜이 무엇을 할지 알 수 있게 했습니다.

6. 같은 힌트를 동시에 요청할 때

입력 해시에 유니크 제약을 두어, 먼저 등록한 요청만 LLM을 호출하고 나머지는 저장된 결과를 받게 했습니다. 학생이 달라도 문제와 질문이 같으면 결과를 공유해 비용이 한 번만 듭니다.
