5:T18b2,<p>Ait는 개발자의 이력서·GitHub를 바탕으로 질문하는 AI 모의면접과 화상 스터디를 연결한 서비스다. 나는 6인 팀의 프론트엔드 리더를 맡았다.</p>
<p>면접과 스터디 화면을 구현하면서 반복해서 마주한 문제는 <strong>여러 사람이 만든 화면을 사용자가 하나의 서비스로 이해할 수 있게 하는 것</strong>이었다. 같은 상태를 다르게 부르거나 화면에 필요한 정보가 API에 없을 때, 공통 기준과 요청을 구체화하는 일이 필요했다.</p>
<h2>1. 화면을 만들기 전에 상태와 다음 행동을 정했다</h2>
<p>첫 커밋은 화면이 아니라 작업 규칙 문서였다. 이어 디자인 시스템과 도메인 규칙을 정리했다.</p>

<p>Figma 가이드를 개발에서 재사용할 수 있는 공통 값으로 옮기고, 디자인 시스템과 도메인 규칙을 팀원과 AI 코딩 에이전트에게 함께 전달했다. 사용자에게 같은 의미의 상태와 행동을 보여주려면, 구현하는 쪽의 해석도 맞아야 했다.</p>
<p>다만 문서를 공유하는 것만으로 일관성이 완성되지는 않았다. 실제 화면을 보며 기준과 어긋나는 부분을 다시 조정해야 했다.</p>
<h2>2. 화면에서 발견한 차이를 규칙의 보완으로 연결</h2>
<p>Ait의 강조색은 골드였다. 처음에는 카드 테두리와 칩, 진행 표시 등 여러 곳에 색이 들어가 강조가 분산됐다. 그래서 섹션 하나에 한두 곳만 사용하고, 나머지는 짙기나 그림자로 표현하도록 기준을 정했다. 규칙을 만든 나도 같은 기준으로 화면을 다시 봐야 했다.</p>
<p>반대의 문제도 있었다. 어떤 화면에는 가이드 밖의 표현이 필요했는데, 에이전트가 기존 문서를 근거로 변경을 거부했다. 규칙에 없는 상황을 처리할 방법이 부족했던 것이다.</p>
<p>이 경험을 통해 <strong>공통 기준과 예외를 판단할 기준을 함께 정해야 한다</strong>는 과제를 얻었다. 화면마다 임의로 바꾸는 것과, 기존 기준이 맞지 않는 상황을 검토해 보완하는 것은 구분할 필요가 있었다.</p>
<h2>3. ‘연동이 안 된다’를 필요한 정보와 조건으로 바꿨다</h2>
<p>API 연동이 시작되자 목업과 실제 데이터가 섞인 화면이 생겼다. 나는 API 명세 35개를 기준으로 화면을 대조하고, 누락 항목을 연동 요청 문서로 정리했다.</p>
<p>예를 들어 스터디 목록에는 현재 인원수 필드가 없었다. 그래서 현재 응답으로 표시할 수 있는 ‘정원 6명’을 먼저 보여주고, ‘3/6명’처럼 표시하려면 필요한 현재 인원수 필드를 요청했다. 같은 필드가 다른 API에 있다는 점도 함께 전달하고, 프론트엔드는 해당 응답이 들어오면 연결할 수 있도록 준비했다.</p>
<p>파일 업로드가 실패할 때도 요청 형식이 명세와 일치하는지 확인하고, 로컬 Windows와 배포 Linux의 경로 차이 등 백엔드에서 확인할 항목을 문서로 넘겼다.</p>
<p>요청에는 다음 정보를 담으려 했다.</p>
<ul>
<li>어느 화면에서 어떤 정보나 동작이 필요한가?</li>
<li>현재 응답과 구현으로 어디까지 가능한가?</li>
<li>프론트엔드에서 확인한 범위는 어디까지인가?</li>
<li>상대 파트에서 무엇을 확인하거나 추가하면 되는가?</li>
</ul>
<p><strong>기능 이름만 전달하는 것보다 화면의 요구와 현재 계약의 차이를 구체화하는 일</strong>이 협업의 기준이 됐다. 다른 파트의 코드를 바로 수정하는 대신 필요한 변경과 담당 범위를 공유했다. 에이전트의 작업 범위도 문서에 명시했다.</p>
<h2>4. 완성도와 실제 상태를 기준으로 보여줄 내용을 정리</h2>
<p>랜딩 페이지에는 모션과 3D 연출을 만들었지만, 완성도가 부족한 회차별 리포트 비교 섹션은 제거했다. 카드 틸트와 일부 배경 효과도 덜어냈다. 실사용자가 없는 프로젝트에 사용자 후기를 넣지도 않았다.</p>
<p>도메인 규칙에는 목업 데이터와 미연동 기능을 실제 완료된 결과처럼 표현하지 않는 기준을 남겼다. 어떤 화면을 보여줄지 결정할 때 시각적인 완성도와 함께 <strong>사용자에게 전달하는 상태가 실제와 맞는지</strong> 확인했다.</p>
<p>이 선택이 사용성을 높였는지는 별도 검증이 필요하다. 당시에는 보여줄 수 있는 기능과 설명을 실제 구현 상태에 맞추는 데 집중했다.</p>
<h2>5. 결과와 남은 협업 과제</h2>
<p>면접·스터디·리포트 화면을 구현하고, 디자인과 상태 기준, API 연동 요청을 문서로 남겼다. 최종 발표에서는 자료 제작과 시연을 맡았다. 수상으로 이어지지는 않았다.</p>
<p>마감 직전에 연동과 확인 작업이 몰렸고, 팀 안에서 개발과 관리의 역할이 한쪽에 집중된 점도 돌아보게 됐다. 프론트엔드 리더로서 관리 작업을 더 일찍 나눠 맡고, 구현 후 연결하고 검증하는 시간까지 계획했어야 했다.</p>
<p>다음에는 화면별로 입력·상태·예외·완료 조건을 먼저 맞추고, API 연동 확인을 일정에 포함하려고 한다. 문서의 수보다 <strong>다른 사람이 같은 의미로 이해하고 다음 작업을 시작할 수 있는지</strong>를 기준으로 정리하겠다.</p>
