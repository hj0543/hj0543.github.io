이 집은 어느 학교에 갈까 — 학군 정보와 비교 기준 설계

댓글 —좋아요 —조회 —

가까운 학교와 통학구역 정보를 구분하고, 검색·비교·AI 추천에서 같은 점수와 근거를 사용하도록 정리한 과정.

SSAFYHomefit서비스 기획데이터비교 기준

Homefit은 사용자의 금융 상황과 주거 선호를 함께 확인하는 부동산 탐색 서비스다. 나는 지도 검색과 비교, 공공데이터 연동 등을 맡았다. 학군 기능을 만들며 먼저 정해야 했던 것은 계산 방법보다 사용자가 학교 정보를 보고 무엇을 판단하려는지였다.

1. 가까운 학교와 통학구역에 해당하는 학교를 구분

처음에는 매물에서 가장 가까운 초등학교를 찾으면 된다고 생각했다. 하지만 거리만으로는 사용자가 궁금해하는 통학구역 정보를 설명할 수 없었다.

그래서 ‘가까운 학교가 어디인가’와 ‘이 매물의 좌표가 어느 통학구역에 속하는가’를 구분했다. 후자는 당시 수집한 초등학교 통학구역·중학교 학교군의 경계와 학교 연계 데이터를 사용해 판정했다. 매물의 좌표가 어느 구역 안에 들어가는지 확인하는 방식이다.

이 화면은 사용한 학구도 데이터에 따른 결과다. 실제 배정을 확정하는 정보와 혼동되지 않도록 데이터의 기준과 표시 의미도 함께 관리해야 한다. 핵심은 사용자의 질문이 서로 다른데 같은 ‘학교 정보’로 뭉뚱그리지 않는 것이었다.

2. 같은 매물의 점수가 화면마다 달랐다

학군 정보는 매물 찾기, 후보 비교, AI 추천에서 사용했다. 처음에는 검색·비교와 AI 추천의 계산식이 달라 같은 집에 서로 다른 점수가 붙었다.

사용자는 화면을 바꿨을 뿐인데 비교 기준도 바뀌는 셈이었다. 나는 계산을 백엔드의 공통 서비스로 모으고, 검색·비교·추천이 같은 결과를 사용하도록 바꿨다. AI 분석에도 화면에 표시하는 학군·학교 거리 정보를 전달했다.

구분한 정보 서비스에서의 의미
통학구역 수집한 구역 데이터에 매물 좌표가 포함되는지
학교 거리·도보시간 학교에 접근하는 데 필요한 거리와 이동 정보
학교 통계·학원 분포 당시 설정한 교육환경 비교 점수의 입력
종합 점수 여러 항목을 가중 평균한 프로젝트의 자체 비교 기준

통학구역의 포함 여부와 종합 점수는 다른 판단이다. 같은 계산을 쓰도록 통일하는 것과, 그 점수가 사용자의 선호를 적절히 반영하는지도 구분해 검토해야 한다.

3. 점수의 입력 범위와 데이터가 없을 때의 처리도 정책

점수를 구성하면서 NEIS 학교 통계와 학원 밀집도를 추가했다. 학원은 교과목 학원만 반영하도록 범위를 조정했다. 미술·음악·체육·뷰티까지 같은 항목으로 세면 의도한 비교 기준과 다른 정보가 점수를 끌어올릴 수 있었기 때문이다.

데이터가 없는 경우도 정해야 했다. NEIS 통계 항목을 단순히 빼고 나머지로 평균을 내면 결측이 있는 매물이 오히려 높은 점수를 받는 상황이 생겼다. 당시 구현에서는 해당 항목에 45점을 부여하는 규칙을 뒀다.

여섯 항목의 가중치와 결측 점수는 당시의 설계값이다. 이 값이 교육의 질이나 학업 성과를 입증하는 것은 아니다. 어떤 정보가 포함되는지와 결측 처리 방식이 순위에 어떤 영향을 주는지를 함께 확인해야 한다고 봤다.

4. 비교 정보를 제공할 수 있도록 데이터 처리 범위를 조정

통학구역 판정에는 많은 꼭짓점을 가진 공간 데이터가 필요했다. 지도에서 매물을 불러올 때마다 모든 구역을 비교하면 계산이 반복됐다.

구역을 감싸는 사각형으로 후보를 먼저 줄인 뒤 실제 포함 여부를 판정하고, 같은 단지의 매물은 좌표 단위로 결과를 재사용하도록 했다. 목록에는 학군 요약과 점수를 전달하고, 경계 도형은 사용자가 오버레이를 켤 때 별도로 불러오게 했다.

사용자에게 필요한 비교 결과를 먼저 제공하면서, 자세한 경계 정보는 요청할 때 볼 수 있도록 응답을 나눈 것이다. 구체적인 데이터와 판정 코드는 아래에 남겼다.

5. 결과와 다음에 검증할 기준

매물의 통학구역을 확인하고, 검색·비교·AI 추천이 같은 학군 점수와 근거를 사용하도록 구현했다. 이 작업은 데이터의 의미, 계산 기준, 화면에서의 설명을 맞추는 과정이었다.

다음에는 사용자가 통학구역과 학교 거리, 자체 점수를 서로 구분해 이해하는지 확인하고 싶다. 가중치나 결측 처리에 따라 후보 순위가 얼마나 바뀌는지, 데이터가 부족한 매물을 어떻게 표시해야 하는지도 검토할 과제다.

구현과 당시 계산 기준

사용 데이터 규모, 구역 포함 판정 코드와 가중치·결측 처리 펼치기

당시 사용한 데이터와 반복 계산의 규모

판정 자체는 어렵지 않았다. 문제는 횟수였다. 전국 학구도는 초등 통학구역만 7,123개, 중학교 학교군이 1,685개다. 폴리곤 하나의 꼭짓점은 중앙값으로 초등 277개, 중학교 1,150개이고, 큰 것은 1만 개를 넘는다.

시연용 매물은 38,258건이었다. 모든 매물을 모든 초등 통학구역과 비교하면 약 2억 7천만 번의 판정이 필요하고, 판정 한 번마다 꼭짓점 수백 개를 돈다. 지도 화면에서 매물 목록을 불러올 때마다 이걸 할 수는 없었다. 그래서 처음부터 이 횟수를 줄이는 쪽으로 설계했다.

후보 구역 필터와 좌표 단위 재사용

대부분의 비교는 볼 필요도 없는 비교였다. 분당의 매물을 춘천의 학구도와 맞춰 볼 이유는 없다.

그래서 전처리 단계에서 학구도마다 폴리곤을 감싸는 사각형(bbox)을 계산해 함께 저장했다. 판정은 두 단계로 나눴다.

  1. 매물 좌표가 bbox 안에 드는 학구도만 후보로 남긴다. 사각형 비교라 DB 쿼리 하나로 끝난다.
  2. 남은 후보에만 실제 point-in-polygon을 적용한다.
def find_containing_zone(latitude, longitude, school_level):
    candidates = SchoolZone.objects.filter(
        school_level=school_level,
        min_latitude__lte=latitude,
        max_latitude__gte=latitude,
        min_longitude__lte=longitude,
        max_longitude__gte=longitude,
    )
    for zone in candidates:
        if point_in_geojson(latitude, longitude, zone.geometry_geojson):
            return zone
    return None

대부분의 학구도가 1단계에서 떨어져 나가니, 비싼 판정은 매물마다 몇 번이면 충분했다.

횟수를 줄일 곳이 하나 더 있었다. 같은 단지의 매물은 좌표가 같다. 38,258건의 매물도 좌표로 묶으면 매물이 있는 단지 894곳뿐이었다. 그래서 판정 결과를 좌표 단위로 캐시해, 같은 단지의 매물은 한 번만 판정하게 했다.

여러 조각과 구멍을 가진 도형 판정

학구도가 전부 하나의 다각형은 아니었다. 초등 통학구역 7,123개 중 906개는 여러 조각으로 나뉜 MultiPolygon이었다. 한 학교의 구역이 길이나 하천을 사이에 두고 떨어져 있는 경우다. 이때는 조각 중 하나에만 들어가도 그 학교 구역이다.

GeoJSON 규격에서는 폴리곤의 첫 번째 링이 바깥 경계이고, 나머지 링은 구멍이다. 실제 데이터에 구멍 난 폴리곤은 없었지만, 규격대로 "바깥 경계 안에 있고, 구멍에는 들어가지 않는다"로 판정을 정리해 두었다.

def _point_in_polygon(latitude, longitude, polygon):
    if not polygon or not _point_in_ring(latitude, longitude, polygon[0]):
        return False
    return not any(_point_in_ring(latitude, longitude, hole) for hole in polygon[1:])


def point_in_geojson(latitude, longitude, geometry_geojson):
    geometry = _loads_geojson(geometry_geojson)
    coordinates = geometry.get('coordinates') or []
    if geometry['type'] == 'Polygon':
        return _point_in_polygon(latitude, longitude, coordinates)
    if geometry['type'] == 'MultiPolygon':
        return any(_point_in_polygon(latitude, longitude, polygon) for polygon in coordinates)
    return False

링 안에 있는지는 레이 캐스팅으로 판정했다. 점에서 한 방향으로 선을 그었을 때 경계와 홀수 번 만나면 안쪽이다.

목록과 경계 정보 응답 분리

학구도 GeoJSON은 좌표가 많아 무겁다. 목록에 함께 담으면 응답의 대부분을 폴리곤이 차지하는데, 정작 사용자가 학군 오버레이를 켜지 않으면 쓰이지도 않는다.

목록에는 판정 결과(학군 요약과 점수)만 담고, 폴리곤은 지도에서 학군 오버레이를 켤 때만 별도 API로 내려받도록 나눴다.

프로젝트 당시의 점수 구성

학군은 매물 찾기, 매물 비교, AI 추천 세 곳에서 쓰였다. 그런데 처음에는 점수를 계산하는 공식이 두 개였다.

  • 매물 찾기·비교: 기본 40점에 통학구역 포함 여부, 가장 가까운 초·중학교 거리, 반경 1km 학교 수를 더하는 방식
  • AI 추천: 가장 가까운 학교 거리 65%, 반경 1km 학교 수 35%를 섞는 방식

같은 집인데 매물 찾기와 AI 추천이 서로 다른 학군 점수를 내놓았다. 같은 집을 두고 화면마다 다른 말을 하는 서비스는, 사용자에게 어느 쪽도 믿지 못하게 만든다.

학군 점수 계산을 백엔드 서비스 하나로 모았다. 매물 찾기와 비교를 먼저 옮기고, 다음 날 AI 추천도 같은 서비스를 쓰게 바꿨다. 옮기면서 공식도 다시 세웠다. 거리와 학교 수만 보던 점수에 NEIS 학교 통계와 학원 밀집도를 더해, 여섯 항목의 가중 평균으로 계산한다.

항목 가중치
초등학교 도보 시간 12
중학교 도보 시간 20
반경 1km 학교 수 8
학급당 학생 수 (NEIS) 22
교원 1인당 학생 수 (NEIS) 18
반경 1km 교과목 학원 20

각 항목을 0~100점으로 환산한 뒤 가중 평균을 낸다. 학원은 이때 기준을 다시 잡아 교과목 학원만 세도록 바꿨다. 미술, 음악, 체육, 뷰티 학원까지 세면 학군과 거리가 먼 학원도 점수를 끌어올렸다. 입시·보습 학원은 1.5배, 외국어 학원은 1.3배처럼 종류별로 가중치를 두었다. NEIS 통계가 없는 학교는 해당 항목을 빼지 않고 45점을 매겼다. 빼고 나머지로만 평균을 내면 데이터가 빈 매물이 오히려 높은 점수를 받았기 때문이다.

계산하는 곳이 하나가 되자, AI 매물 분석에도 화면에 보이는 것과 같은 학군·학교 거리 정보를 넘길 수 있었다.

위 가중치와 결측 처리값은 당시 구현 기준이며, 사용자 선호나 교육 성과에 대한 검증 결과와는 구분한다.
