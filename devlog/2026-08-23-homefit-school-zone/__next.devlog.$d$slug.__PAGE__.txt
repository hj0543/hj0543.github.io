5:T2246,<p>Homefit은 SSAFY 1학기 종합 프로젝트(관통 프로젝트)로 만든 부동산 추천 서비스다. 사용자의 금융 상황과 주거 선호를 받아 감당할 수 있는 매물을 찾아 준다. 주거 선호 중에서 가장 까다로웠던 건 학군이었다. &quot;이 집에 살면 아이가 어느 학교에 가는가&quot;라는 질문에 답해야 했다.</p>
<h2>1. 가까운 학교가 내 학교는 아니다</h2>
<p>처음에는 매물에서 가장 가까운 초등학교를 찾으면 된다고 생각했다. 그런데 초등학교는 거리가 아니라 통학구역으로 배정된다. 길 하나를 사이에 두고 바로 앞 학교가 아니라 더 먼 학교로 가는 경우도 있다.</p>
<p>그래서 거리 대신 학구도를 썼다. 학구도는 학교마다 통학구역의 경계를 폴리곤으로 그려 둔 데이터다. 질문이 &quot;매물 좌표가 어느 폴리곤 안에 들어가는가&quot;로 바뀌었다. 전형적인 point-in-polygon 문제다.</p>
<p>데이터는 한국지방교육행정연구재단이 공개한 초등학교 통학구역, 중학교 학교군 SHP 파일과 학교-학구 연계정보를 썼다. 전처리 단계에서 SHP 도형을 GeoJSON 문자열로 바꿔 CSV에 담고, 그대로 DB에 적재했다.</p>
<p><img src="/projects/Homefit_old/home_compare_1.png" alt="비교표의 &#39;배정 초등학교&#39; 행이 학구도 판정 결과다"></p>
<h2>2. 매물 수 × 폴리곤 수</h2>
<p>판정 자체는 어렵지 않았다. 문제는 횟수였다. 전국 학구도는 초등 통학구역만 7,123개, 중학교 학교군이 1,685개다. 폴리곤 하나의 꼭짓점은 중앙값으로 초등 277개, 중학교 1,150개이고, 큰 것은 1만 개를 넘는다.</p>
<p>시연용 매물은 38,258건이었다. 모든 매물을 모든 초등 통학구역과 비교하면 약 2억 7천만 번의 판정이 필요하고, 판정 한 번마다 꼭짓점 수백 개를 돈다. 지도 화면에서 매물 목록을 불러올 때마다 이걸 할 수는 없었다. 그래서 처음부터 이 횟수를 줄이는 쪽으로 설계했다.</p>
<h2>3. 상자로 먼저 거르기</h2>
<p>대부분의 비교는 볼 필요도 없는 비교였다. 분당의 매물을 춘천의 학구도와 맞춰 볼 이유는 없다.</p>
<p>그래서 전처리 단계에서 학구도마다 폴리곤을 감싸는 사각형(bbox)을 계산해 함께 저장했다. 판정은 두 단계로 나눴다.</p>
<ol>
<li>매물 좌표가 bbox 안에 드는 학구도만 후보로 남긴다. 사각형 비교라 DB 쿼리 하나로 끝난다.</li>
<li>남은 후보에만 실제 point-in-polygon을 적용한다.</li>
</ol>
<pre><code class="language-python">def find_containing_zone(latitude, longitude, school_level):
    candidates = SchoolZone.objects.filter(
        school_level=school_level,
        min_latitude__lte=latitude,
        max_latitude__gte=latitude,
        min_longitude__lte=longitude,
        max_longitude__gte=longitude,
    )
    for zone in candidates:
        if point_in_geojson(latitude, longitude, zone.geometry_geojson):
            return zone
    return None
</code></pre>
<p>대부분의 학구도가 1단계에서 떨어져 나가니, 비싼 판정은 매물마다 몇 번이면 충분했다.</p>
<p>횟수를 줄일 곳이 하나 더 있었다. 같은 단지의 매물은 좌표가 같다. 38,258건의 매물도 좌표로 묶으면 매물이 있는 단지 894곳뿐이었다. 그래서 판정 결과를 좌표 단위로 캐시해, 같은 단지의 매물은 한 번만 판정하게 했다.</p>
<h2>4. 여러 조각으로 나뉜 폴리곤</h2>
<p>학구도가 전부 하나의 다각형은 아니었다. 초등 통학구역 7,123개 중 906개는 여러 조각으로 나뉜 MultiPolygon이었다. 한 학교의 구역이 길이나 하천을 사이에 두고 떨어져 있는 경우다. 이때는 조각 중 하나에만 들어가도 그 학교 구역이다.</p>
<p>GeoJSON 규격에서는 폴리곤의 첫 번째 링이 바깥 경계이고, 나머지 링은 구멍이다. 실제 데이터에 구멍 난 폴리곤은 없었지만, 규격대로 &quot;바깥 경계 안에 있고, 구멍에는 들어가지 않는다&quot;로 판정을 정리해 두었다.</p>
<pre><code class="language-python">def _point_in_polygon(latitude, longitude, polygon):
    if not polygon or not _point_in_ring(latitude, longitude, polygon[0]):
        return False
    return not any(_point_in_ring(latitude, longitude, hole) for hole in polygon[1:])


def point_in_geojson(latitude, longitude, geometry_geojson):
    geometry = _loads_geojson(geometry_geojson)
    coordinates = geometry.get(&#39;coordinates&#39;) or []
    if geometry[&#39;type&#39;] == &#39;Polygon&#39;:
        return _point_in_polygon(latitude, longitude, coordinates)
    if geometry[&#39;type&#39;] == &#39;MultiPolygon&#39;:
        return any(_point_in_polygon(latitude, longitude, polygon) for polygon in coordinates)
    return False
</code></pre>
<p>링 안에 있는지는 레이 캐스팅으로 판정했다. 점에서 한 방향으로 선을 그었을 때 경계와 홀수 번 만나면 안쪽이다.</p>
<h2>5. 폴리곤은 필요할 때만</h2>
<p>학구도 GeoJSON은 좌표가 많아 무겁다. 목록에 함께 담으면 응답의 대부분을 폴리곤이 차지하는데, 정작 사용자가 학군 오버레이를 켜지 않으면 쓰이지도 않는다.</p>
<p>목록에는 판정 결과(학군 요약과 점수)만 담고, 폴리곤은 지도에서 학군 오버레이를 켤 때만 별도 API로 내려받도록 나눴다.</p>
<h2>6. 학군 점수는 한 곳에서</h2>
<p>학군은 매물 찾기, 매물 비교, AI 추천 세 곳에서 쓰였다. 그런데 처음에는 점수를 계산하는 공식이 두 개였다.</p>
<ul>
<li><strong>매물 찾기·비교</strong>: 기본 40점에 통학구역 포함 여부, 가장 가까운 초·중학교 거리, 반경 1km 학교 수를 더하는 방식</li>
<li><strong>AI 추천</strong>: 가장 가까운 학교 거리 65%, 반경 1km 학교 수 35%를 섞는 방식</li>
</ul>
<p>같은 집인데 매물 찾기와 AI 추천이 서로 다른 학군 점수를 내놓았다. 같은 집을 두고 화면마다 다른 말을 하는 서비스는, 사용자에게 어느 쪽도 믿지 못하게 만든다.</p>
<p>학군 점수 계산을 백엔드 서비스 하나로 모았다. 매물 찾기와 비교를 먼저 옮기고, 다음 날 AI 추천도 같은 서비스를 쓰게 바꿨다. 옮기면서 공식도 다시 세웠다. 거리와 학교 수만 보던 점수에 NEIS 학교 통계와 학원 밀집도를 더해, 여섯 항목의 가중 평균으로 계산한다.</p>

<h2>돌아보며</h2>
<ul>
<li>문제를 바로 풀기 전에, 질문을 맞게 세웠는지 먼저 본다. &quot;가까운 학교&quot;와 &quot;배정되는 학교&quot;는 다른 질문이다.</li>
<li>비싼 연산 앞에는 싼 필터를 둔다.</li>
<li>응답에는 화면이 지금 쓰는 것만 담는다.</li>
<li>같은 숫자를 여러 화면에서 보여준다면 계산하는 곳은 하나여야 한다.</li>
</ul>
<p>지도 위의 점 하나가 어느 선 안에 들어가는지 묻는 일이 이렇게 많은 질문을 품고 있을 줄 몰랐다. 좌표와 폴리곤만 보면 단순한 기하 문제지만, 그 뒤에는 누군가의 아이가 매일 걸어갈 등굣길이 있었다. 숫자 하나가 틀리면 누군가는 잘못된 기대를 안고 집을 보러 갈 수도 있다. 처음 공간 데이터를 다뤄 본 관통 프로젝트에서, 데이터 너머의 사람을 떠올리는 법을 배웠다.</p>
