역 도보 5분, 정말 5분일까 — 도보시간 계산을 세 번 바꾼 이야기

댓글 —좋아요 —조회 —

역 도보 시간 계산을 직선거리에서 ODsay 실시간 조회, 로컬 OSRM 사전 계산으로 세 번 바꾸며 만난 API 한도와 경로 데이터 문제를 정리한 기록.

SSAFYHomefit백엔드

블로그를 열기 전 노션에 정리해 두었던 기록을 옮겨 온 글이다. 날짜는 노션에 처음 적은 날을 따랐다.

Homefit은 SSAFY 1학기 관통 프로젝트로 만든 부동산 추천 서비스다. 매물 찾기에는 "역 도보 N분 이내" 필터가 있고, AI 추천에는 역까지의 거리로 매기는 교통 점수가 있다. 둘 다 결국 "이 단지에서 역까지 걸어서 몇 분인가"라는 숫자 하나에 기대고 있었다. 그 숫자를 구하는 방식을 6월 22일부터 이틀 동안 세 번 바꿨다.

1. 직선거리를 80으로 나누던 시절

처음 방식은 단지와 역 사이의 직선거리를 구하고, 사람이 1분에 80m를 걷는다고 보고 나눴다.

_WALK_M_PER_MIN = 80
_STATION_MAX_WALK_MIN = 30
_STATION_MAX_DISTANCE_M = _WALK_M_PER_MIN * _STATION_MAX_WALK_MIN

매물 찾기의 필터도 같은 식이었다. "역 도보 5분 이내"를 고르면 역에서 반경 5 × 80 = 400m 안에 있는 매물을 보여 줬다.

하지만 직선거리는 실제로 걷는 길을 반영하지 못한다. 직선으로는 가까워도 그 사이에 하천이나 큰 도로, 담장으로 막힌 단지가 있으면 실제로는 한참 돌아가야 한다.

안양시 만안구 박달동의 한 단지에서 광명역까지가 그런 경우였다. 직선거리는 2.1km라 1분에 80m로 환산하면 약 26분이다. 하지만 사이에 안양천과 고속도로가 있어, 건널 수 있는 다리까지 돌아가는 실제 도보 경로는 48분이 걸렸다.

필터는 "역 도보 N분 이내"를 1분 단위로 고를 수 있게 되어 있어서, 이런 오차가 생기면 매물이 전혀 다른 구간에 들어갔다.

6월 22일, 직선거리로 도보시간을 환산하는 코드를 전부 주석 처리했다. 실제 도보 경로를 얻기 전까지는 분 단위 숫자를 아예 보여 주지 않고, 반경 거리(m)만 쓰기로 했다. 틀린 숫자를 보여 주느니 보여 주지 않는 편이 낫다고 판단했다.

2. ODsay를 실시간으로 부르다

실제 경로를 얻으려고 처음 고른 것은 ODsay였다. 프로젝트에서 이미 대중교통 소요시간을 구하는 데 쓰고 있던 길찾기 API인데, 같은 키로 쓸 수 있는 maasRP라는 경로 API가 있었다. 이동 수단을 SearchMethod=1, 즉 도보로만 지정하면 걸어서 가는 경로를 돌려준다.

def fetch_walk_min(from_lat, from_lng, to_lat, to_lng) -> int | None:
    response = requests.get(
        _ODSAY_MAAS_URL,
        params={
            "SX": from_lng, "SY": from_lat,
            "EX": to_lng,   "EY": to_lat,
            "SearchTime": _default_search_time(),
            "SearchMethod": "1",   # 도보만
            "lang": 0, "output": "json", "apiKey": api_key,
        },
        timeout=_TIMEOUT,
    )
    paths = response.json().get("result", {}).get("paths", [])
    ...

추천 결과가 나오면 상위 20개 매물마다 가까운 역까지 이 API를 불러 도보시간을 채웠다. 같은 날 오후에는 카드에 역을 하나가 아니라 노선별 대표역을 최대 3개까지 보여 주도록 바꿨다. 호출 수는 매물 수 × 역 수가 됐다. 하나씩 기다리지 않도록 ThreadPoolExecutor(max_workers=8)로 동시에 보냈다.

호출하는 곳은 계속 늘었다. 같은 날 마이페이지에 직장 정보를 넣으면 직장까지 출퇴근 시간을 붙이는 기능도 maasRP로 만들었다. 역까지 800m가 넘는 매물에는 대중교통 소요시간도 따로 조회했다. 다음 날 아침에는 학군 점수의 초·중학교 도보 시간 항목까지 같은 함수를 부르게 했다. 학군 점수는 추천 후보 전체와 매물 비교, 상세 화면에서 모두 계산되니, 매물 하나마다 호출이 두 번씩 더 붙었다.

3. 한도에 걸리다

이 방식은 하루 만에 막혔다. 6월 23일 오전, 추천 API에서 대중교통 조회를 끄면서 이런 주석을 남겼다.

# 4-2. ODsay 대중교통 API — 한도 초과로 비활성화 (transit_min은 ComplexStationWalk DB 사용)
# enrich_transit_info(top)

한도 초과는 추천 결과에서 도보시간이 전부 비어 나오는 걸 보고 알았다. 추천 한 번에 상위 20개 매물마다 역을 최대 3개씩 조회하니 도보 호출만 최대 60번이었다. 역이 먼 매물의 대중교통 조회와 학군 점수의 학교 도보 조회까지 더하면 많게는 100번이 넘었다. 팀원과 함께 테스트하며 추천을 몇 번만 돌려도 하루 한도가 금방 찼다.

한도 문제를 정리하다 보니 구조 자체가 잘못됐다는 걸 알았다. 단지와 역의 위치는 바뀌지 않으니, 둘 사이의 도보시간은 누가 언제 요청하든 같은 값이다. 그런데 이 값을 요청이 올 때마다 외부 API에 다시 묻고 있었다.

4. 한 번만 계산해 두기 — 로컬 OSRM

그래서 요청마다 계산하지 않고, 모든 단지에 대해 미리 계산해 DB에 넣어 두기로 했다.

계산에는 OpenStreetMap 도로 데이터로 경로를 구하는 오픈소스 엔진 OSRM을 썼다. 일주일 전 전처리 스크립트에서 공개 OSRM 데모 서버로 도보시간을 구해 본 적이 있는데, 이번에는 localhost:5000에 서버를 직접 띄웠다.

데모 서버는 짧은 시험용이라 대량 요청에는 맞지 않았다. 535개 단지마다 역 3개, 학교 2개를 조회하면 요청이 수천 번인데, 직접 띄운 서버는 호출 한도를 신경 쓸 필요가 없었다.

수집은 Django 관리 명령으로 만들었다. 수집 대상인 성남시 분당구와 안양시 만안구의 단지 좌표를 모으고, 단지마다 반경 안의 역을 거리순으로 최대 3개 골라 OSRM에 도보 경로를 묻는다.

for rank, station in enumerate(nearby, 1):
    walk_min = _fetch_walk_min_osrm(lat, lng, station['latitude'], station['longitude'])
    time.sleep(delay)

    transit_min = None
    if station['distance_m'] > TRANSIT_SKIP_M:   # 800m 이내 역은 대중교통 조회 생략
        transit_min = _fetch_transit_min_odsay(lat, lng, station['latitude'], station['longitude'], api_key)
        time.sleep(delay)

    writer.writerow({...})

대중교통 시간은 여전히 ODsay에서 받지만, 이제는 수집할 때 한 번뿐이다. 역까지 800m가 넘는 경우에만 묻고, 호출 사이에는 --delay 0.3초씩 쉰다. 중간에 끊겨도 --resume을 주면 이미 처리한 좌표는 건너뛰고 이어서 수집한다.

결과는 CSV로 먼저 저장하고, load_walk_times 명령으로 ComplexStationWalk, ComplexSchoolWalk 테이블에 한 번에 적재했다. 학교 쪽도 같은 방식으로 단지마다 가장 가까운 초등학교와 중학교까지의 도보시간을 저장했다.

이제 추천 API는 요청 시작에 DB를 한 번 읽어 (위도, 경도) → {역 이름: 도보시간} 사전을 만들고, 매물마다 거기서 찾기만 한다.

def _load_station_walk_index() -> dict:
    idx: dict = {}
    for row in ComplexStationWalk.objects.values('latitude', 'longitude', 'station_name', 'walk_min'):
        if row['walk_min'] is None:
            continue
        key = (row['latitude'], row['longitude'])
        idx.setdefault(key, {})[row['station_name']] = row['walk_min']
    return idx

ODsay 도보 호출과 ThreadPoolExecutor는 지우고, fetch_walk_min()은 예전 호출부가 깨지지 않게 항상 None만 돌려주도록 남겼다. DB에 값이 없는 지역은 외부 API 대신 직선거리 기준 점수로 물러서고, 학교는 직선거리에 도시 보행 우회율 1.3을 곱해 추정한다. 데이터 1차 생성부터 DB 적재, 실시간 호출 제거까지 6월 23일 오전 한나절에 끝났다.

같은 날 오후에는 팀원이 역 탐색 반경을 2.4km에서 5km로 넓혀 전체를 다시 수집했다. 판교처럼 역이 멀리 떨어진 단지도 역 정보를 가질 수 있게 하기 위해서다. 지금 데이터에서 가장 가까운 역이 2.4km 밖에 있는 단지가 35곳인데, 이전 반경이었다면 이 단지들에는 역이 하나도 잡히지 않았다.

5. 신호 대기 시간 보정하기

OSRM이 돌려주는 시간은 길을 따라 쉬지 않고 걸었을 때의 시간이라, 횡단보도에서 신호를 기다리는 시간이 빠져 있다. 경로가 길수록 건너야 할 횡단보도도 많아지니 차이도 커진다.

그래서 수집 단계에서 OSRM 시간에 보정 계수를 곱했다. 짧은 길은 1.05배에서 시작해 경로 길이에 비례해 늘고, 1,750m 이상이면 1.40배로 고정된다.

WALK_FACTOR_MIN = 1.05
WALK_FACTOR_MAX = 1.40
WALK_FACTOR_SCALE_M = 1750

def _crosswalk_factor(distance_m: float) -> float:
    ratio = min(distance_m / WALK_FACTOR_SCALE_M, 1.0)
    return WALK_FACTOR_MIN + (WALK_FACTOR_MAX - WALK_FACTOR_MIN) * ratio

보정을 넣고 역과 학교 데이터를 다시 수집했다. 예를 들어 한 단지에서 오리역까지는 직선으로 596m다. 예전 방식이라면 7.5분이고, 보정 전 OSRM으로는 9.9분, 보정 후에는 12.0분이 됐다.

점수는 DB로 옮기면서 도보시간 기준으로 다시 세웠다. 도보 5분까지는 100점, 10분이면 70점, 19분이면 30점으로 구간마다 선형으로 깎이고, 그 뒤로는 20점이다. 역까지 멀어 대중교통 시간이 있는 경우에는 도보 점수와 대중교통 점수 중 높은 쪽을 쓴다. 걸어서 25분 걸리는 역도 대중교통으로 10분이면 그 집의 교통 사정은 나쁘지 않기 때문이다. 매물 찾기의 "역 도보 N분 이내" 필터도 DB가 생긴 직후 반경 400m 같은 환산을 버리고, 저장된 도보시간으로 직접 거르도록 바꿨다.

6. 동천역과 동천

데이터를 열어 보니 이상한 줄이 있었다.

apt_seq,lat,lng,rank,station_name,lines,distance_m,walk_min,transit_min
41135-185,37.33687,127.11461,2,동천역,신분당선,1044,30.8,18
41135-185,37.33687,127.11461,3,동천,신분당선,1044,31.3,17

같은 역이 "동천역"과 "동천"이라는 두 이름으로 들어 있었다. 역 테이블에 두 표기가 모두 있었는데, 수집 스크립트는 이름이 글자 그대로 같은 역만 하나로 묶었다. 정자, 판교, 미금, 모란도 마찬가지였고, 535개 단지 중 181곳에서 같은 역이 상위 3개 자리를 두 번 차지했다.

조회하는 쪽에서 이름 끝의 "역"을 떼어 같은 키로 묶고, 값이 둘이면 더 짧은 도보시간을 남겼다.

def _normalize_station_name(name: str) -> str:
    text = str(name or '').strip()
    return text[:-1] if text.endswith('역') else text

다만 수집 단계에서는 여전히 이름 그대로 역을 묶는다. 그래서 일부 단지는 3개 중 한 자리를 같은 역에 쓰고 있다. 다시 한다면 수집 전에 역 이름부터 표준화할 것이다.

결과

최종 데이터는 535개 단지, 단지당 역 3개씩 1,605행이다. 같은 535개 단지를 기준으로, 방식마다 "역 도보 5분·10분 이내"에 드는 단지 수를 다시 세어 봤다.

방식 5분 이내 10분 이내
직선거리 ÷ 80m (400m·800m 반경) 135곳 293곳
OSRM 도보 경로 70곳 216곳
OSRM + 횡단보도 보정 45곳 162곳

처음 방식이 "역 도보 5분"이라고 보여 주던 단지 중 실제 경로로도 5분 안에 닿는 곳은 절반 남짓이었다. 보정까지 넣으면 3분의 1이다.

추천 API는 이제 역과 학교 도보시간 때문에 외부 API를 부르지 않는다. 직장까지의 출퇴근 시간만은 지금도 maasRP를 실시간으로 부른다. 직장 좌표는 사용자마다 달라서 미리 계산해 둘 수 없기 때문이다.

돌아보며

  • 단지와 역 사이 도보시간처럼 요청마다 같은 값은 처음부터 미리 계산해 DB에 두는 게 맞았다. 실시간 호출로 시작한 탓에 한도에 걸리고 나서야 구조를 바꿨다.
  • 외부 API 호출을 하나 붙일 때마다 매물 수만큼 호출이 늘었다. 기능을 붙이기 전에 한 요청에서 몇 번 호출되는지 먼저 계산했어야 했다.
  • 정확한 도보시간을 구하기 전까지 분 단위 숫자를 빼고 거리만 보여 준 판단은 지금 봐도 맞았다고 생각한다.
  • 역 이름 중복은 조회하는 쪽에서 맞췄지만, 이미 수집된 데이터에는 같은 역이 두 자리를 차지한 채 남았다. 역 이름은 수집 단계에서 표준화(정제)했어야 했다.

"역 도보 5분"은 부동산 광고에서 흔히 보는 문구인데, 직접 계산해 보기 전에는 그 숫자를 의심해 본 적이 없었다. 앞의 오리역 예시처럼 직선거리로 7.5분인 경로가 실제 길과 신호 대기까지 반영하면 12분이 됐다. 그래서 Homefit에서는 보정한 도보시간을 기준으로 필터와 점수를 계산하도록 했다.
