<h2>2. 수준에 맞는 문제를 고르기</h2>
<p>기존 봇들은 난이도와 알고리즘 유형을 함께 걸어 검색하기 어려웠다. &quot;실버 1 수준의 BFS 문제&quot;처럼 스터디 수준에 맞춰 고르고 싶었다.</p>
<p>Solved.ac API v3 문서를 읽어 보니 검색 쿼리에 티어와 태그 조건을 함께 넣을 수 있었다. &quot;실1&quot;, &quot;BFS&quot;처럼 스터디원들이 평소 부르는 이름을 공식 티어 번호와 태그 키로 바꿔 주는 표를 만들고, 여기에 <code>lang:ko</code>를 더해 한글 문제만 받아 오게 했다. 그렇게 받은 후보 중 다섯 문제를 추천한다.</p>

<h2>3. 같은 문제가 자꾸 추천됐다</h2>
<p>쓰다 보니 문제가 생겼다. 같은 조건으로 여러 번 추천을 받으면 이전에 나온 문제가 계속 다시 나왔다.</p>
<p>처음에는 API가 돌려준 후보 중 <code>random.sample()</code>로 다섯 개를 뽑았다. 하지만 결과는 크게 달라지지 않았다. 원인은 뽑는 쪽이 아니라 후보 쪽에 있었다. API가 돌려주는 후보 목록 자체가 매번 비슷했다. 같은 바구니에서 아무리 섞어 뽑아도 나오는 건 결국 그 바구니 안의 것들이었다.</p>
<p>그래서 검색 쿼리에 <code>sort:random</code>을 넣고, 요청마다 무작위 값을 함께 보내 같은 응답이 캐시되어 돌아오지 않게 했다. 후보 자체가 무작위로 섞인 뒤에 다섯 개를 뽑으니, 그제야 추천이 고르게 퍼졌다.</p>
<pre><code class="language-python"># utils/solvedac.py
full_query = &quot; &quot;.join(query_parts) + &quot; sort:random&quot;

params = {
    &quot;query&quot;: full_query,
    &quot;direction&quot;: &quot;asc&quot;,
    &quot;page&quot;: 1,
    &quot;c&quot;: random.randint(1, 1000000)  # CDN 캐시를 우회하기 위한 무작위 값
}

# cogs/study.py
selected_problems = random.sample(ko_problems, min(len(ko_problems), 5))
</code></pre>
<p>클라이언트에서 아무리 무작위로 골라도 원본이 고정되어 있으면 소용이 없다. 외부 API를 쓸 때는 그 API가 어떻게 정렬하고 캐시하는지까지 알아야 한다는 걸 이때 배웠다.</p>
<h2>4. 누가 풀었는지 대신 확인하기</h2>
<p>공지를 올린 뒤에는 누가 풀었는지 확인하는 일이 남았다. 봇이 5분마다 Solved.ac API로 스터디원들의 풀이 기록을 확인하고, 공지된 문제를 풀면 알림 채널에 알려 주도록 했다. 마감이 지난 문제는 감지 목록에서 알아서 빠진다. 쌓인 기록은 <code>/문제풀이현황</code>으로 주간, 월간, 누적 풀이 수를 한눈에 볼 수 있게 했다.</p>

<h2>5. 재시작하면 기록이 사라졌다</h2>
<p>연동 정보와 풀이 집계를 메모리에만 들고 있으면, 서버가 재시작되거나 봇을 다시 배포할 때 그동안 쌓은 기록이 사라질 수 있었다.</p>
<p>실제로 한 번 그런 일이 있었다. 봇을 업데이트하고 다시 띄웠더니, 일주일 동안 쌓인 풀이 집계가 전부 0으로 돌아가 있었다. 숫자는 다시 쌓으면 되지만, 함께 쌓아 온 흐름이 끊긴 기분은 꽤 오래 남았다.</p>
<p>규모가 작아서 데이터베이스까지는 필요 없다고 판단했다. 대신 상태가 바뀔 때마다 JSON 파일에 저장하고, 시작할 때 다시 읽어 오도록 했다.</p>
<p>기능이 늘면서 저장 형식도 바뀌었다. 처음엔 문제 번호만 담던 목록이 마감일과 공지일을 함께 담게 됐다. 이미 쌓인 기록을 버릴 수는 없어서, 이전 형식을 읽으면 새 형식으로 바꿔 주는 코드를 남겼다.</p>

<h2>6. 혼자 운영하는 서버</h2>
<p>봇은 24시간 떠 있어야 했다. Oracle Cloud의 무료 인스턴스에 올리고, Python 가상환경과 <code>.env</code>로 토큰을 분리했다. 프로세스는 pm2에 맡겨 두니, 죽어도 알아서 다시 올라왔다.</p>
<p>스터디원도 직접 띄워 볼 수 있게 단계별 배포 가이드도 써 두었다.</p>
<p>수정할 때마다 서버에 접속해 코드를 받고 다시 켜는 일도 곧 반복이 됐다. 결국 이것도 넘겼다. master에 푸시하면 GitHub Actions가 서버에 접속해 코드를 받고, 의존성을 설치하고, pm2로 봇을 다시 띄운다.</p>
<pre><code class="language-yaml">on:

<p>그래도 한 번은 봇이 조용히 멈췄다. 알림이 오지 않는다는 메시지를 받고서야 알았다. Solved.ac가 응답을 주지 않자 요청이 끝나지 않고 매달려 있었고, 그동안 봇도 함께 멈춰 있었다. 프로세스는 살아 있는데 일은 하지 않는 상태. 재시작 설정으로는 막을 수 없는 종류의 장애였다. 그 뒤로 모든 요청에 5초 타임아웃을 걸고, 스터디원 한 명의 확인이 실패해도 나머지는 계속 확인하도록 고쳤다. 혼자 운영한다는 건, 아무도 대신 지켜봐 주지 않는다는 뜻이었다.</p>

<p>몇 달 동안 매일 들여다보던 봇이 하루아침에 할 일을 잃었다. 코드는 그대로인데, 딛고 서 있던 바닥이 사라진 것이다. 외부 서비스 위에 지은 프로젝트는 그 서비스보다 오래 살 수 없다는 걸 그때 실감했다.</p>
