스터디장의 반복 작업을 봇에게 넘기기 — 사용하며 바꾼 운영 흐름

댓글 —좋아요 —조회 —

8인 스터디의 반복 업무를 명령어와 알림으로 바꾸고, 사용 중 드러난 중복 추천·기록 유실·조회 장애를 개선한 과정.

개인 프로젝트Discord Bot서비스 기획운영 개선

SSAFY 1학기 동안 8명이 참여하는 알고리즘 스터디를 주 3회 운영했다. 문제를 고르고 링크를 붙이고 마감을 적은 뒤, 누가 풀었는지 확인하는 일이 매번 반복됐다.

Discord 봇은 이 공지 작성을 줄이는 데서 시작했다. 이후 추천과 집계, 기록 유지와 장애 처리로 범위가 넓어졌다. 이 글은 기능 목록보다 사용하면서 어떤 문제를 발견했고 왜 다음 기능이나 정책이 필요해졌는지를 정리한 기록이다. 현재 봇 운영은 중단한 상태다.

1. 매번 바뀌는 정보와 반복되는 형식을 구분

공지의 내용은 달라져도 필요한 항목은 같았다. 문제 제목과 링크, 마감일, 참여자가 반응할 이모지였다. 그중 운영자가 직접 결정할 정보는 문제와 마감일이고, 제목·난이도·태그는 API에서 가져올 수 있었다.

그래서 문제 번호 최대 3개와 마감일을 입력하면 나머지를 채우는 공지 명령어를 만들었다. 문제별 번호 이모지도 자동으로 붙였다.

처음 사용한 날 스터디원 한 명이 ‘다른 스터디에서도 쓸 수 있느냐’고 물었다. 이 반응은 다른 운영자에게도 비슷한 반복 작업이 있을 수 있다는 단서였다. 다만 다른 스터디의 요구와 사용 방식까지 확인한 것은 아니므로, 우선 우리 스터디의 흐름을 개선하는 데 집중했다.

2. 추천 조건은 스터디가 쓰는 표현으로 입력

문제를 찾을 때 필요한 조건은 난이도와 알고리즘 주제였다. ‘실버 1 수준의 BFS 문제’처럼 두 조건을 함께 고르고 싶었다.

‘실1’, ‘골5’, ‘BFS’, ‘너비우선탐색’ 같은 표현을 API의 난이도 번호와 태그로 바꾸고, 한글 문제 중 후보 5개를 추천하게 했다. 외부 서비스의 검색 문법을 사용자가 직접 조합하지 않아도 되도록 입력을 설계했다.

3. 반복 사용에서 드러난 추천의 문제

같은 조건으로 여러 번 추천받으면 이전 문제가 자주 다시 나왔다. 처음에는 응답으로 받은 목록에서 무작위로 다섯 개를 골랐지만, 원본 후보가 비슷하면 결과도 크게 달라지지 않았다.

원인을 후보 목록까지 거슬러 확인하고, 검색 정렬과 캐시 응답을 고려하도록 바꿨다. 무작위로 정렬된 후보에서 다시 뽑는 방식으로 추천 구성을 개선했다.

추천은 한 번 조건에 맞는 결과를 보여주는 것뿐 아니라 다시 눌렀을 때도 탐색할 후보를 제공하는지 살펴봐야 했다. 기능이 작동한다는 확인과 반복 사용의 경험은 다른 기준이었다.

4. 공지 이후의 확인과 참여 안내도 연결

공지 뒤에는 누가 풀었는지 확인하는 일이 남았다. 봇이 5분마다 공지 문제의 풀이 기록을 조회하고, 풀이 알림을 보내게 했다. 마감이 지난 문제는 감지 목록에서 정리했다.

주간·월간·누적 현황은 명령어로 확인하고 매일 밤 9시에는 리마인드를 보냈다. 운영자가 개별 기록을 찾아보던 일을 스터디원도 함께 볼 수 있는 정보로 바꿨다.

누군가의 풀이 알림이 올라오면 다른 스터디원이 문제를 여는 모습을 봤다. 이 반응은 참여율의 정량적 개선과 구분해 운영 중 관찰로 남겼다. 진행 상황을 보여주는 기능이 어떤 행동과 연결되는지 계속 살펴볼 필요가 있었다.

5. 기록 유실과 무응답을 겪고 운영 기준을 추가

업데이트 후 봇을 다시 띄웠더니 일주일간 쌓인 집계가 초기화된 적이 있었다. 결과를 보여주는 기능을 만들었지만, 재배포 뒤에도 그 기록이 남아 있어야 한다는 요구를 충분히 반영하지 못했다.

작은 규모에 맞춰 JSON 파일에 상태를 저장하고 시작할 때 복원하도록 바꿨다. 저장 형식이 달라진 뒤에도 이전 기록을 읽어 변환하도록 했다.

또 한 번은 프로세스가 실행 중인데 알림이 오지 않았다. 외부 API 요청이 끝나지 않아 확인 작업이 대기하고 있었다. 프로세스 재시작 설정만으로는 이 문제를 해결할 수 없었다.

모든 요청에 5초 타임아웃을 두고, 한 명의 조회 실패가 나머지 참여자의 확인까지 중단시키지 않게 처리했다. 이후 기능을 볼 때는 정상 결과뿐 아니라 기록 유지와 실패가 영향을 미치는 범위도 함께 확인하게 됐다.

6. 실제로 쓰이는 도구를 운영하며 남긴 기준

공지 생성에서 시작해 조건별 추천, 풀이 확인·알림·집계와 기록 복원까지 연결했다. Oracle Cloud에서 운영하고 GitHub Actions와 프로세스 관리 도구로 배포·재시작을 구성했으며, 스터디원이 직접 배포할 수 있도록 가이드도 작성했다.

이 경험에서 확인한 변화는 반복 수작업을 명령어와 주기적 확인으로 바꿨다는 것이다. 다시 운영한다면 공지 작성·현황 확인에 걸린 시간, 반복 추천 빈도, 외부 조회 실패와 복구 기록을 남겨 개선 전후를 비교하고 싶다.

기획의 출발점은 내 반복 작업이었지만, 사용한 뒤에는 어떤 입력이 번거로운지, 어떤 결과가 다시 쓰이는지, 어디서 흐름이 끊기는지가 다음 작업을 정하는 기준이 됐다.
