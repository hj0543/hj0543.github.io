## 프로젝트 개요

> 오늘의 금융 행동이 목표일을 바꿉니다.

**도담**은 사용자가 세운 금융 목표를 기준으로 계좌·소비·카드·대출·예적금 데이터를 통합 진단하고, 목표 달성을 방해하는 요인을 찾아 개선 행동별 효과를 수치로 비교해 주는 개인 금융 코치 앱입니다.
"어린아이가 탈 없이 잘 자라는 모양"이라는 뜻처럼, 청년의 금융생활과 자산이 무리 없이 건강하게 자라도록 돕는 것을 목표로 합니다.

SSAFY 교육용 금융망 데이터를 바탕으로 **보여 주고 → 찾아내고 → 상담하고 → 행동하는** 흐름을 한 앱에서 제공합니다.

## 개발 배경 및 필요성

600만 원을 모으려고 청년미래적금에 매달 50만 원을 넣으면 12개월이 걸립니다. 여기에 매달 10만 원만 덜 쓰면 10개월, **목표가 2개월 당겨집니다.** 그런데 그 10만 원을 **어디서** 아껴야 할까요?

- 기존 자산관리 앱은 금융현황과 소비내역을 **보여주는 데** 강점이 있지만, 지금 상태가 **내 목표 달성에 적절한지**는 알려주지 않음
- 소비 증가, 높은 대출금리, 유휴자금처럼 개선 여지가 여러 개 겹칠 때 **무엇부터 고쳐야 효과적인지** 판단하기 어려움
- 소비를 줄이거나 대출 조건을 바꾸는 선택이 목표 달성 시점에 **얼마나 영향을 주는지** 미리 확인할 수 없음
- 카드결제·대출상환·적금납입·월세가 겹치는 시점의 **단기 현금 부족**을 사전에 알기 어려움

→ "목표 기준으로 개선 요인을 탐지 → 행동별 효과를 비교 → 실행 이후 변화를 추적"하는 코치형 서비스가 필요하다고 판단했습니다.

## 주요 기능

- **목표 설정** — "얼마를, 언제까지": 모으기 목표(목표 금액·기한 → 필요 월 저축액, 예상 달성일)와 줄이기 목표(월 소비 예산 → 남은 가용액·소비 속도)
- **세이프박스(도담 계좌)**: 도담 전용 계좌 하나에 목표별 금액을 나눠 담고 꺼냄. 기존 계좌 ↔ 도담 계좌 간은 금융망 실제 이체
- **발견(진단)** — "무엇이 목표를 방해하나": 카테고리 소비 급증·고금리 대출·목표 달성 지연·잔액 부족을 규칙으로 탐지하고, K-Means 소비 유형 군집으로 또래 대비 위치를 보조 진단
- **시뮬레이션** — "이 선택을 하면 목표가 얼마나 당겨지나": 소비 감소, 저축 변경, 예적금 가입, 신규 대출·추가상환·대환, 할부·리볼빙·현금서비스와 이들을 조합한 복합 시나리오의 목표 달성일 변화 비교
- **금융 리포트** — "뭐부터 할지, 했는지": 금융 효율 점수, 소비 유형과 또래 비교, 시계열 소비 예측과 그 근거
- **토리(AI 코치)**: 서버가 계산한 진단·추천·예측·시뮬레이션 수치로만 답하는 금융 상담
- **현금흐름 예측**: 예정 입출금을 일 단위로 시뮬레이션해 잔액 부족 시점과 심각도를 미리 경고
- **가계부와 자산**: 달력형 거래 내역, 카테고리 소비 분석, 계좌·카드·대출·예적금 조회와 이체
- **알림·로그인**: 결제·상환 예정, 현금흐름 위험, 목표 FCM 푸시 / 카카오·구글 소셜 로그인

## 기술적 고민 및 문제 해결

### 1. LLM은 계산하지 않는다 — 환각 없는 AI 금융 코치
- **문제**: 금융에서 AI 환각은 허용될 수 없음. LLM이 금리·기간을 직접 계산하면 그럴듯하지만 틀린 숫자가 사용자에게 전달됨
- **해결**: LLM에게는 **도구 선택과 문장 생성만** 맡기고 계산은 전부 서버 엔진이 수행
  - 입력 가드에서 계좌·카드번호·이메일 등 민감정보 차단 → LLM 1차 호출로 도구 8종(소비 절감·저축액 변경·중도상환·대환·복합 시뮬레이션, 목표 달성 예측·최신 진단·소비 예측 조회) 중 선택. ID·계좌번호는 인자로 받지 않음
  - 서버의 진단·추천·K-Means·시계열·시뮬레이션 엔진이 계산한 facts만 LLM 2차 호출에 전달해 3문장·200자 이내로 설명
  - 출력 가드가 **facts에 없는 숫자**를 발견하면 템플릿 문장으로 대체, LLM 장애 시에도 응답
- **효과**: 화면의 숫자는 facts에서만 나오고, LLM은 검증된 계산 결과를 쉬운 말로 설명하는 역할로 한정됨

### 2. 시계열 소비 예측 — 학습 없이 서버에서 즉시 계산
- **문제**: "다음 달 얼마나 쓸까"를 보여주고 싶지만 사용자별 이력이 짧고, 여행·이사 같은 일회성 지출이 섞여 있으며, 별도 학습 서버를 둘 여유가 없음
- **해결**: 월 단위 **감쇠 추세 지수평활(Damped Trend Exponential Smoothing)** 채택
  - 이상치 정리: 중앙값에서 MAD × 3 이상 벗어난 달은 잘라 일회성 지출 영향 제거
  - 수준 α = 0.5: 한 달 튄 소비에 과민 반응하지 않음 / 추세 감쇠 φ = 0.85: "계속 늘어난다"는 과장 예측 방지
  - 예측 구간 Z = 1.28: 숫자 하나가 아닌 80% 범위로 불확실성까지 전달
  - 이력 3개월 이상이면 수준 + 추세, 12개월 이상이면 명절·연말 계절성까지 반영
  - 거래가 없던 달은 0이 아니라 결측으로 처리 — 0을 넣으면 수준이 끌려 내려가 휴면 구간이 있는 사용자의 예측이 절반 이하로 떨어짐
- **효과**: `수준 + 추세분 + 계절분 = 예상액`이 원 단위로 정확히 성립하도록 응답을 분해해, 리포트 카드와 AI 코치가 같은 근거를 그대로 보여줌

### 3. 목표별 계좌 연동 → 도담 계좌 + 세이프박스로 방향 전환
- **문제**: 처음에는 목표 하나에 여러 계좌를 연결해 저축 속도를 계산했음. 예적금은 매달 일정하지만 입출금 계좌는 소비와 섞여 금액이 불규칙했고, 앞의 시계열 모델을 적용해 봐도 예측 구간이 끝없이 벌어져 **저축 속도를 예측할 수 없었음**. 목표가 늘수록 입출금 계좌도 여러 개 새로 만들어야 했음
- **해결**: 사용자당 **도담 전용 계좌 하나**를 금융망에 개설하고, 목표별 금액은 계좌 안의 세이프박스에 나눠 담는 구조로 전환. 기존 계좌 ↔ 도담 계좌 이동만 실제 이체이고, 담기·꺼내기는 목표별 배정 원장(`safebox_movement`)에 기록하는 내부 배정. 저축 속도는 이 원장의 최근 완료 월 순증감으로 계산
  - 배정 합계를 넘는 출금은 409로 차단, 사용자 행 잠금으로 배정·출금·동기화를 직렬화
  - 금융망 계좌 개설 전에 시도 기록을 별도 트랜잭션으로 남겨, 타임아웃처럼 결과가 불명확한 경우 중복 개설을 막음
- **효과**: 계좌는 하나로 유지하면서 목표별 진행률과 예상 달성일을 안정적으로 계산할 수 있게 됨

### 4. 시뮬레이션 중복 실행 방지와 재현성
- **문제**: 같은 조건으로 여러 번 실행하면 결과 행이 쌓이고, 상품 금리가 바뀌면 같은 요청도 다른 결과가 나와 이전 결과와 비교할 수 없음. 요청 파라미터가 JSON이라 DB UNIQUE로 막을 수 없음
- **해결**: `(userId, type, 정규화된 입력 지문, 기준일, 계산 버전)`의 SHA-256 요청 해시를 저장해 같은 날 같은 지문이면 기존 건을 반환(200), 새 조건이면 생성(201). 동시 요청은 사용자 행 `PESSIMISTIC_WRITE` 잠금으로 직렬화. 계산식이 바뀌면 계산 버전을 올려 이전 결과를 재사용하지 않음
- **효과**: before/after 스냅샷이 보존되어 조건 변경 전후 비교가 가능하고, 복합 시나리오 자식 9종의 순서를 바꿔도 집계 결과가 같음을 통합 테스트로 고정

### 5. 진단 → 추천 → 시뮬레이션 간 계산 일관성
- **문제**: 추천이 제시한 효과(예: 월 20만 원 절감)와 실제 시뮬레이션 결과가 다르면 서비스를 신뢰할 수 없음
- **해결**: 추천 생성기가 현재 데이터를 재계산하지 않고 **진단이 저장한 스냅샷만** 읽도록 순수 함수로 설계. 추천 응답에 시뮬레이션 프리셋(엔드포인트 + 요청 본문)을 포함해 클릭 한 번으로 같은 값을 실행. `추천 효과 = 시뮬레이션 after − before` 등식을 API 수준 테스트로 고정하고, 예상 달성일은 목표 도메인과 같은 식·같은 기준일로 계산
- **효과**: 규칙 버전을 명시해 규칙 변경 시 캐시 재사용 범위가 분리됨

### 6. 현금흐름 위험 판정 시점
- **문제**: 하루 마감 잔액으로 판정하면 여러 출금 중 어느 건에서 막히는지 알 수 없고, 한 번 음수가 되면 이후 날짜가 전부 위험으로 잡힘
- **해결**: 하루 안에서 입금을 먼저 반영한 뒤 **각 출금 직전 잔액**으로 판정. 탐지를 잔액 순회 계산기 안에서 함께 수행해 입출금 반영 순서가 두 곳으로 갈라지지 않도록 함
- **효과**: 위험이 "어느 날 어떤 출금에서 얼마 부족"으로 특정되어 진단·추천의 입력으로 그대로 연결

### 7. 민감한 금융 정보 보호
- **문제**: 카드번호·계좌번호를 조회 키로 써야 하지만 원문 저장·단순 해시는 유출 시 복원 가능
- **해결**: 암호화 키와 분리된 키를 쓰는 **HMAC-SHA-256 해시 컬럼**으로 조회, 원문은 **AES-256-GCM**(매번 새 IV)으로 암호화, 응답은 마스킹 값만 제공. 모든 리소스 조회에 소유권 조건을 넣고, 타인 리소스는 존재 여부를 노출하지 않도록 404 처리
- **효과**: 응답·로그·시뮬레이션 스냅샷 어디에도 원문·해시가 남지 않음을 테스트로 검증

- **부하 테스트(팀)**: k6로 로그인 → 계좌 → 카드 → 대출 → 진단 → 추천 실제 사용자 흐름을 재현해 **100만 요청 오류율 0.00%**, 지속 처리량 약 **796 req/s**, 22분 연속 부하에서 메모리·커넥션 누수 없음 (24개월·139만 건 거래 데이터 기준)
