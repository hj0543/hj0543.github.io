6명이 백엔드 셋, 프론트, 인프라로 나뉘어 3개월짜리 프로젝트를 하고 있다. 나는 백엔드에서 카드·대출·예적금·진단·추천·시뮬레이션을 맡았다. 도메인이 많다 보니 내 코드는 남의 도메인 데이터를 끊임없이 읽고, 그러다 보면 남의 영역에서 이상한 것을 발견하는 일이 매주 생긴다.

이번 주만 해도 이런 것들을 만났다.

- 카드 목록 API에 `cardId`가 없어서 프론트가 리볼빙 시뮬레이션에 넣을 값을 얻을 경로가 없다.
- 전체 테스트 빌드에서 갑자기 96건이 `Table "auth_session" not found`로 죽었다. 내가 건드린 적 없는 인증 도메인 테스트다.
- 시연 seed 데이터의 대출 상환일이 9월 고정값이라 9월 21일부터는 시연 계정에 추가상환할 대출이 없다.

셋 다 "발견한 사람이 고치면 10분"처럼 보인다. 그런데 셋 다 고치지 않았다. 이 글은 왜 안 고쳤는지, 대신 무엇을 했는지에 대한 기록이다.

## 1. 고치면 빠르지만 팀은 느려진다

`cardId` 추가는 정말 한 줄이다. DTO에 필드 하나 넣으면 끝. 하지만 카드 목록 API의 응답 형식은 루트 API 명세서에 박혀 있고, 그 명세서는 프론트가 타입을 뽑는 기준이다. 내가 슬쩍 필드를 추가하면 명세와 코드가 어긋나고, 프론트는 "문서엔 없는데 응답엔 있는 필드"를 만난다. 다음 사람은 어느 쪽이 맞는지 다시 확인해야 한다.

96건 실패는 더 위험했다. 원인을 파 보니 내가 `@SpringBootTest` 컨텍스트를 2개 더한 게 방아쇠였다. 공유 H2 인메모리 DB를 쓰는 기존 테스트들이 Spring 컨텍스트 캐시 축출에 취약했고, 컨텍스트 수가 임계를 넘자 `create-drop`이 다른 컨텍스트의 테이블을 날렸다. 해법은 캐시 크기를 늘리거나 테스트 DB URL을 분리하는 것인데, 그건 `application-test.yml`이라는 **공용 설정**을 바꾸는 일이다. 깨지는 테스트는 전부 다른 사람 도메인이다. 내가 고치면 그 사람은 자기 테스트 설정이 왜 바뀌었는지 모른 채 다음 컨텍스트를 추가하다 같은 문제를 다시 만난다.

그래서 내 쪽에서는 새 테스트가 기존 컨텍스트를 공유하도록 바꿔 **우회**만 했고, 근본 수정은 기록해서 넘겼다.

## 2. "넘긴다"는 것의 형식

넘긴다는 게 슬랙에 한 줄 던지는 것이라면 안 하느니만 못하다. 받는 사람은 맥락이 없고, 일주일 뒤엔 나도 없다. 그래서 백엔드 문서 폴더에 `remaining-work.md`라는 파일을 두고, 발견한 것마다 같은 네 항목으로 적기로 했다.

```markdown
### 테스트 컨텍스트 캐시와 공유 H2

- [ ] 공유 H2와 create-drop을 쓰는 기존 통합 테스트가 Spring 컨텍스트 캐시 축출에
      취약하다. maxSize 상향 또는 DB URL 분리를 검토한다.
- 근거: 587에서 새 컨텍스트 2개를 더한 첫 전체 빌드에서 96건이 실패했다.
       같은 커밋의 깨끗한 worktree는 통과했으므로 컨텍스트 수 증가가 원인이다.
- 선행 조건: 공용 테스트 설정 변경이라 팀 확인이 필요하다.
- 담당 근거: BE-B 소관이 아니다. 깨지는 테스트는 BE-A 도메인이고 설정은 공용이다.
           587은 발견·기록만 했으며 담당은 팀에서 정한다.
- 완료 조건: 컨텍스트를 추가해도 전체 빌드가 순서와 무관하게 통과한다.
```

네 항목이 각각 다른 질문에 답한다.

- **근거**: 왜 이게 문제라고 생각하는가. 재현 조건과 배제한 가설까지. "깨끗한 worktree는 통과했다"가 없으면 받는 사람은 내 로컬 환경 문제를 의심하는 데서 시작해야 한다.
- **선행 조건**: 왜 지금 내가 안 하는가. 권한이 없어서인지, 결정이 필요해서인지, 다른 작업이 먼저여야 하는지.
- **담당 근거**: 누가 해야 한다고 보는가, 그리고 **왜**. 여기가 제일 중요하다. "BE-A가 하세요"가 아니라 "깨지는 테스트가 BE-A 도메인이고 설정이 공용이라서"까지 적어야 받는 사람이 동의하거나 반박할 수 있다.
- **완료 조건**: 뭐가 되면 끝인가. 이게 없으면 "검토한다"로 끝나는 항목은 영원히 검토 중이다.

이 형식이 좋은 이유는 **적는 사람이 판단을 미룰 수 없다**는 것이다. "담당 근거"를 채우려면 이게 정말 남의 일인지 한 번 더 생각해야 한다. 실제로 `Jira 원문 미확인` 항목은 이 칸을 채우다가 "본인 이슈다. 티켓으로 올리지 않고 직접 확인한다"로 결론이 났다. 넘길 게 아니었던 것이다.

## 3. 넘긴 것과 고친 것을 같은 곳에 두지 않는다

발견 사항을 처리하는 갈래는 세 개다.

1. **내 범위 안이면 고친다.** 이번 MR에 포함.
2. **내 범위 밖이면 기록하고 넘긴다.** remaining-work.md + 담당자에게 전달.
3. **결정이 필요하면 결정을 요청한다.** 누가 고칠지가 아니라 어느 쪽이 맞는지가 불명확할 때.

3번의 예가 소비 추천 프리셋이었다. 추천이 제안한 감소액이 시뮬레이션의 상한을 넘으면 실행이 400이 된다. 프리셋을 조립할 때 상한으로 잘라 넣을 수도 있고, 프론트가 사용자에게 값을 고치게 할 수도 있다. 둘 다 말이 된다. 내가 하나를 고르면 프론트 담당자는 결정된 뒤에 알게 된다. 그래서 "팀 결정"으로 두고 프론트 이슈 번호를 적어 전달했다.

핵심은 1번과 2·3번을 **같은 MR에 섞지 않는 것**이다. 테스트를 추가하는 MR 안에 운영 코드 수정이 슬쩍 들어가면 리뷰어는 diff 200줄에서 그 5줄을 찾아내야 한다. MR 제목이 "Test: ○○ 테스트 고정"이면 리뷰어는 테스트만 볼 권리가 있다.

## 4. 문서 폴더가 대화를 대신할 때

이 프로젝트에서는 이슈 하나를 시작할 때 계획서(`simulation-618-plan.md`)를 먼저 쓰고, 끝나면 같은 파일 마지막에 "실행 결과" 절을 붙인다. 계획서에는 범위·근거·fixture·단언·위험이 들어가고, 실행 결과에는 "설계에서 달라진 점"이 들어간다.

처음엔 과하다고 생각했다. 그런데 쓰다 보니 계획서가 두 가지 일을 했다.

- **리뷰어의 진입점.** MR 본문의 "리뷰 포인트"에 계획서 §3.2를 링크하면 "왜 이 필드는 집합으로 비교하나"를 코드 주석 없이 설명할 수 있다.
- **다음 이슈의 근거.** 618 계획서 §1이 "587 후속 4건 중 세 번째"라고 적혀 있어서, 619를 잡는 사람은 587 계획서 §4로 거슬러 올라가면 왜 이 검증이 필요했는지를 만난다.

오늘 만든 QA 결과 기록용 README도 같은 발상이다. 팀원 6명이 각자 QA를 하면 6가지 형식이 나온다. 스프린트 끝에 "지금 시연 가능한가"를 판단하려면 6개를 다 읽고 머릿속에서 합쳐야 한다. 형식을 하나로 고정하면 — 파일명 규칙, 판정값 세 개(`통과`/`실패`/`진행 불가`), 심각도 네 단계, 결함은 반드시 Jira에도 등록 — 읽는 비용이 쓰는 비용으로 옮겨진다. 쓰는 사람은 한 번 쓰고, 읽는 사람은 여러 번 읽으니 그게 맞다.

README에서 가장 신경 쓴 규칙은 "재수행하면 새 파일을 만들고 이전 파일은 수정하지 않는다"였다. QA 1차 결과를 2차에서 덮어쓰면 "1차에서 뭐가 깨졌고 2차에서 뭐가 고쳐졌나"가 사라진다. 이력이 목적인데 이력을 지우는 셈이다.

## 정리

- 남의 영역 문제를 발견하면 고치는 것보다 **잘 넘기는 것**이 팀에 더 싸다. 고치면 내 시간 10분, 넘기면 문서 10분인데, 고쳤을 때 팀이 치르는 비용은 보이지 않는다.
- 넘길 때는 근거·선행 조건·담당 근거·완료 조건 네 칸을 채운다. "담당 근거"를 채우다 보면 넘길 게 아닌 것도 걸러진다.
- 고친 것과 넘긴 것을 같은 MR에 섞지 않는다.
- 형식을 고정하면 읽는 비용이 쓰는 비용으로 옮겨진다. 한 번 쓰고 여러 번 읽히니 그게 맞다.
