금융 시뮬레이션 API를 만들면서 "소비 줄이기 + 적금 가입 + 대출 추가상환"처럼 여러 시나리오를 한 번에 돌리는 **복합 시뮬레이션**을 붙였다. 문서에는 처음부터 이렇게 적어 두었다.

> 입력 순서는 지문(fingerprint)에 들어가므로 순서를 바꾸면 별개 요청이지만, 합계는 같다.

그럴듯한 문장이다. 문제는 이걸 실제로 확인한 테스트가 "소비 감소 + 할부" 2개 조합 하나뿐이었다는 것. 자식 유형은 9종이고, 최대 10개까지 넣을 수 있다. 이번 이슈는 그 문장을 자식 9종 전체 조합에서 테스트로 고정하는 일이었다. 운영 코드는 한 줄도 바꾸지 않았는데, 생각보다 배운 게 많아서 정리해 둔다.

## 1. 테스트를 어디에 둘 것인가

처음엔 당연히 계산기 단위 테스트(`CombinedSimulationCalculatorTest`)에 케이스 하나 더 넣으면 될 줄 알았다. 그런데 자식 9종을 다 넣으려면 대출 스냅샷, 예금 상품 옵션, 카드 정보를 전부 손으로 만들어야 한다. 계산기 테스트의 fixture가 지금의 두 배가 된다.

반면 API 통합 테스트(`SimulationIntegrationApiTest`)에는 이미 "10종 시뮬레이션이 모두 실행된다"를 검증하려고 계좌·카드·예금 상품·대출을 DB에 넣어 둔 fixture가 있었다. 여기에 대출 하나만 더 추가하면 9종을 전부 넣을 수 있다.

그래서 이렇게 나눴다.

- 계산기 단위 테스트: 기존 2개 조합 그대로 (합성 로직 자체의 검증)
- API 통합 테스트: 9종 전체 조합의 순서 교환 불변 (계약의 검증)

"단위 테스트가 더 가볍다"는 상식이 fixture 비용 앞에서는 뒤집힐 수 있다. 어느 층에서 검증하는 게 싼지는 매번 다시 봐야 한다.

## 2. 왜 대출이 두 개 필요한가

복합 시뮬레이션에는 충돌 규칙이 있다. 같은 대출에 대해 "추가상환"과 "대환"을 동시에 넣으면 400이다. 추가상환한 대출을 대환한다는 게 의미가 없으니까. 그래서 9종을 다 넣으려면 추가상환용 대출 A와 대환용 대출 B가 따로 있어야 한다.

10번째 자식은 이미 넣은 현금서비스와 같은 유형에 금액만 다른 것으로 채웠다. 중복 검사는 "정규화한 입력이 완전히 같을 때"만 걸리므로 유형이 같아도 금액이 다르면 통과한다. 이런 경계를 fixture로 밟아 보는 것 자체가 검증이다.

## 3. "같다"의 정의가 진짜 작업이었다

세 가지 순서로 실행했다. 명세 순서, 역순, 3칸 회전.

```java
List<String> reversed = new ArrayList<>(children);
Collections.reverse(reversed);
List<String> rotated = new ArrayList<>(children);
Collections.rotate(rotated, 3);
```

그리고 응답을 비교하는데, 여기서 막혔다. 응답 전체를 `isEqualTo`로 비교하면 당연히 실패한다. `simulationId`가 다르고 `createdAt`이 다르다. 그건 예상했다. 문제는 그 다음이었다. **응답의 어떤 필드가 순서에 독립이어야 하고, 어떤 필드는 순서를 따라도 되는가**를 하나하나 정해야 했다.

정리하고 나니 세 부류로 나뉘었다.

**완전히 같아야 하는 것** — 이게 계약의 본체다.

- `before`, `after`(아래 제외 목록 빼고), `comparison`, `cashflow`, `goalImpacts`, `summary`
- `assumptions`: 부모 코드 뒤에 자식 가정의 합집합을 알파벳순으로 붙이도록 설계돼 있어서 그대로 `isEqualTo`가 된다

**순서만 달라야 하는 것** — 입력 순서 보존은 별도 계약이다.

- `scenarios[].sequenceNo`, `after.details.children[]`: 사용자가 넣은 순서대로 돌려주는 게 맞다. 집합으로 비교했다.

**달라도 되는 것**

- `simulationId`, `createdAt`, `request.scenarios` 순서

비교 코드는 결국 "순서를 따르는 목록을 떼어낸 뒤 나머지를 통째로 비교"하는 형태가 됐다.

```java
private JsonNode withoutChildren(JsonNode after) {
    ObjectNode copy = after.deepCopy();
    ((ObjectNode) copy.path("details")).remove("children");
    ((ObjectNode) copy.at("/details/financeCost")).remove("children");
    copy.set("goalImpactDetails", sortedReasons(copy.path("goalImpactDetails")));
    return copy;
}
```

계산을 테스트 안에서 다시 하지 않는다는 원칙을 지켰다. 기대값을 손으로 계산해서 박아 넣으면 계산기 테스트와 중복이고, 계산기 버그를 테스트에 그대로 복사할 위험도 있다. 여기서 확인하고 싶은 건 "값이 맞다"가 아니라 "순서에 무관하다"니까, 세 실행끼리 서로 비교하는 게 정확히 그 질문에 답한다.

## 4. 계획서에 없던 발견 세 가지

계획을 세우고 코드를 돌렸더니 세 군데가 어긋났다. 전부 "결함인가, 계약인가"를 판단해야 하는 항목이었다.

**(1) `financeCost.children`도 순서를 따랐다.** 금융비용 집계 안에 자식별 내역이 또 있었고, 이것도 입력 순서다. `details.children`과 같은 성격이라 제외 목록에 추가했다. 계약에 맞는 동작.

**(2) `title`이 달랐다.** "복합 시나리오 10건: 소비 감소, 저축 변경, …"처럼 자식 제목을 입력 순서로 이어 붙인다. 표시용 문자열이니 순서를 따르는 게 자연스럽다. 건수 접두만 확인하는 것으로 낮췄다.

**(3) `goalImpacts[].reasons`의 원소 순서가 달랐다.** 이게 제일 애매했다. 목표에 영향을 계산할 수 없는 사유 목록인데, 세 실행에서 집합은 같고 순서만 달랐다. 코드를 찾아가 보니 `CombinedCalculator.childReasons`에 "중복 없이 자식 순서대로"라는 주석이 있었다. 설계된 동작이다.

여기서 선택지가 둘이었다. 운영 코드를 고쳐서 `assumptions`처럼 알파벳순으로 정렬하거나, 테스트에서 정렬해 비교하고 넘어가거나. **이번 이슈는 "테스트로 고정한다"이지 "동작을 바꾼다"가 아니다.** 그래서 테스트에서 정렬해 비교하고, "정렬을 고정하고 싶으면 별도 항목"이라고 remaining-work 문서에 남겼다. 테스트를 추가하다가 발견한 것을 그 자리에서 고쳐 버리면 리뷰어는 "테스트 추가" MR 안에서 동작 변경을 찾아내야 한다. 그건 리뷰어에게 못할 짓이다.

## 5. 지문에 순서가 들어간다는 결정

세 실행이 모두 201(신규 생성)이고 `simulationId`가 다르다. 같은 순서로 다시 보내야 200(재사용)이다. 이게 맞는 설계인지 잠깐 다시 생각했다.

순서를 지문에서 빼면 "같은 조합이면 같은 결과"라는 캐시 히트율이 올라간다. 하지만 `scenarios[].sequenceNo`와 `details.children` 순서를 보존한다는 계약과 충돌한다. 저장된 한 행이 두 개의 서로 다른 순서를 동시에 표현할 수는 없다. 결국 지문은 "무엇을 계산했나"가 아니라 "무엇을 요청했나"의 키다. 순서가 요청의 일부라면 지문에도 들어가는 게 일관적이다. 이 테스트는 그 결정을 "세 번 모두 201, 재실행만 200"이라는 단언으로 고정한다.

## 6. 덤: 추천 효과와 시뮬레이션이 같은 숫자를 말하는가

같은 이슈에 대조가 하나 더 있었다. 진단이 "이번 달 예산 초과"를 잡으면 추천이 "월 N원 줄이기"를 제안하고, 그 추천에는 시뮬레이션 프리셋이 달려 있다. 프리셋을 그대로 실행하면 가용자금이 정확히 N원 늘어나야 한다.

그런데 진단은 **이번 달** 거래를 보고, 시뮬레이션 기준선은 **직전 3개월** 평균을 본다. 두 창이 다른 거래를 읽는다. 그래도 등식이 성립하는 이유는 소비 감소 시뮬레이션이 `after = before − reduction`이라는 단순 뺄셈이기 때문이다. 저축 시뮬레이션처럼 날짜가 식에 들어가면 기준일 차이가 결과에 번지지만, 여기는 아니다.

대신 알려진 제한이 하나 드러났다. 감소액이 3개월 평균 지출을 넘으면 400이다. 이번 달에만 유독 많이 썼다면 추천은 큰 감소액을 제안하고, 그 프리셋은 실행이 거부된다. 테스트로 고정하면서 이 제한도 문서에 적고 프론트 쪽에 전달했다(프리셋을 사용자가 수정해서 실행할 수 있게).

## 정리

- 테스트 층은 fixture 비용으로 정한다. 단위가 항상 싼 건 아니다.
- "순서에 무관하다"를 검증할 때 진짜 작업은 응답 필드마다 "같아야 함 / 순서만 달라도 됨 / 달라도 됨"을 분류하는 것이다. 분류 자체가 계약 문서가 된다.
- 세 실행을 서로 비교하면 기대값을 손으로 계산할 필요가 없다.
- 테스트를 추가하다 발견한 것은 기록하고 별도 이슈로 넘긴다. 이번 MR의 이름은 "테스트 추가"다.
